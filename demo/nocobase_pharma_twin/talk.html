Pharma R&D Digital Twin

This page turns a NocoBase prototype of a pharma R&D digital twin, built for a fictional company, into a runnable simulation, built with the DyVE modeling stack (ReactiveDynamics.jl on AlgebraicAgents.jl). It answers the prototype deck's question: is a closed-loop portfolio policy worth it against a static annual plan, over 24 months? The closed loop has two parts: a kill switch that stops a study as soon as a toxicity signal appears, and a monthly reallocation of wet-lab staff. NocoBase stays the system of record. The simulation reads a snapshot of it and writes its results back into NocoBase tables.

All data are synthetic. The portfolio, its programs, compounds, values and events are generated data for a fictional company, and no number on this page is a forecast for a real portfolio. Drug targets are shown as generic labels (Target A to F).

Three decisions this informs

  1. Act on tox flags when they are raisedWorth +$38.3M on its own here. While PRG-402 waits for the annual review, it holds 12 wet-lab FTE and $3.0M a month of CRO spend.
  2. Re-plan wet-lab staff monthlyWorth +$14.1M on its own. The two levers barely interact, so each can be decided separately.
  3. Check PRG-518's kit supply before adding staffWith the assumed batch size and lead time, manufacturing limits this program, not people. The next section shows why.

The static plan acts on the tox flag at the month-12 review, as in the prototype. A portfolio that already acts within a quarter would gain less from the kill switch, because its value is the cost of the months the flagged study keeps running.

    From records to model

    NocoBase keeps the record; the simulation runs the what-if and writes the results back

    We changed no engine code. One Julia file of about 500 lines does the conversion: it reads the NocoBase tables, writes the model out as one JSON file per scenario, and adds two small custom functions that the model calls. A full run of 160 simulated futures takes about two minutes, and the same seed always gives the same numbers on Julia 1.12.

    Before any what-if, the model reproduces the deck's starting point. Its risk-adjusted eNPV of $1,955.2M is the sum of the deck's own rows, recomputed from the tables. The loads on the six resource pools (wet-lab staff plus five shared pools) and the $142.5M quarterly burn, against the deck's $142M, match because the per-program split and the unit costs were chosen to fit them.

    The same mapping, drawn as a map between schemas

    NocoBase's tables and the links between them form a schema C. The model file has its own schema D, made of places, transitions and arcs. The compile step F maps C onto D and carries each core row across one for one. A second map, G, writes the results back into NocoBase's output tables.

    What it leaves out

    What the model leaves out, and whether it changes the answer

    Three gaps bear on the number. The other seven sit with NocoBase, or can be added later without changing the engine.

    1. Only the current stage is simulatedEach program runs to the readout of the stage it is in. Value after the readout is carried by the program's eNPV, not simulated. Simulating later stages, and studies created mid-run, needs an engine feature not yet built (issue #27).
    2. Human decisions run as policiesThe engine cannot pause for an approval, so each human choice runs as its own scenario. The static plan stands for "wait for the annual review".
    3. Queue delays near full useWhen demand exceeds supply, work slows in proportion to the shortfall. The extra waiting that builds up as a lab nears full use is not included, and its effect on the answer has not been tested.
    The other seven gaps, and who would fill them

    Stays with NocoBase

    Out of scope for a simulator.
    1. 4System of record, user interface, roles, natural-language queries, AI memos. The twin reads a snapshot and writes rows back. "Ask the twin" and the AI trade-off memo are built on those rows.
    2. 5Calendar time. The model counts whole months. The run script converts them to dates, fiscal quarters and month-end close.

    Can be added without engine changes

    As a linked model or a custom function.
    1. 6Bayesian update of PoS from assay results. Today a readout is a random pass or fail. An updater would be a separate model that writes program parameters.
    2. 7Machine-learned corrections, kept within constraints (the mockup's f_known + B·r_φ). Hard capacity limits are already built in; a learned correction would be a separate SciML model, linked in.
    3. 8A forward-looking optimizer (MPC). The re-plan is a custom function that a rule calls, so an optimization model written in JuMP could take its place.
    4. 9Checks on the links between models (units, update frequency, data age). Links pass bare numbers today; the one range check is code inside the sending model.

    Engine limit today

    Worked around here; a roadmap candidate.
    1. 10Same-month hand-offs between models. Linked models exchange data with a one-month lag, so patients enrolled in month t reach the portfolio model in month t+1.

    For a portfolio team adopting this

    1. Measure how long a tox flag waitsThe kill switch is worth the months between the flag and the decision. Today's typical wait sets its real value.
    2. Turn the approval choices into a policy tableEach option at the WF2 tox gate (terminate, pivot, wait for review) becomes a scenario, and the twin prices each with its uncertainty.

    For the team running the platform

    1. Run the twin as a NocoBase jobExport, compile, check, simulate and write back as one scheduled job. Dashboards read the scenario rows like any other table, and NocoBase itself does not change.
    2. Add models where the deck needs learning from dataA Bayesian readout updater, an optimizer for the re-plan, and separate supply and finance models, with checked links between them.
    3. Let the model grow during a runEngine work (issue #27) so that WF3 can create studies mid-run and programs can move past one stage.
    4. Let analysts ask new questions with the agent layerThe model files are already in the format the agent skills read, so an analyst can pose a question, add a scenario and get a checked answer from the same files.
    All eight assumptions behind the numbers (recorded in the snapshot under _assumed)
    • Per-readout success. Taken from typical industry phase-transition rates, because the deck gives only cumulative PoS.
    • Months remaining per study. Not in the deck.
    • Per-program resource split. Chosen to reproduce the deck's pool totals.
    • CRO cost and unit costs. Chosen so the burn at T-042 is $142.5M per quarter.
    • Enrollment and site counts. Chosen so PRG-104 enrolls below 0.72 of plan on average (0.65), as in event T-041.
    • Kit stocks, batch sizes and lead time. PRG-518 starts below its reorder point, as in event T-039.
    • PRG-402's hERG IC50. 0.8 µM, below the deck's 1.0 µM kill threshold (event T-042).
    • eNPV lost per month of slip. 1.5%, mostly patent life; the sensitivity chart above shows other values.
