## Context

The maintainer's ask has four parts: inspect an ENSEMBLE of runs; gather STATISTICS (valuations from the ledger); extract "TYPICAL" trajectories for the agentic/stateful tokens; and export. Mapping each onto the current engine:

**Inspecting one run already works** — `state.sol` is a tidy `DataFrame` (`"t"` + one Float64 column per species, written by `save!`, `state.jl`), `state.log` is the per-tick event stream (rows `(:allocation,t,vec)`, `(:saturation,t,…)`, `(:valuation_cost,t,x)`, `(:valuation_reward,t,x)`, `(:valuation,t,x)`, `(:program_ledger,t,Dict)`, `(:terminated_all,t,…)`), and `program_ledger(state)` returns the per-program cost/reward/valuation DataFrame in `(species, creation_index)` order (`ledger.jl:201`). The valuation-from-ledger ask is therefore PARTLY met: per-program cost/reward/valuation exists; what's missing is the cross-run aggregation and the export.

**"Typical" trajectories of agentic tokens DO NOT exist.** We can read a token's FINAL state (`tokens(prob) = collect(values(inners(getagent(prob,"structured"))))`) and its bond audit trail (`past_bonds`, `agents.jl:141-143`; `program_ledger_entries`), but there is no time-indexed history of a token's ATTRIBUTES (its `phase`, `npv_peak`, `pos_remaining`, …) tick by tick. The structural reason is pinned: tokens are PASSIVE agents — `_step!(::AbstractStructuredToken) = nothing` (`agents.jl:135`) — they are acted on by transitions (spawn/bind/`@advance`/finish) but never stepped on their own clock, so they have no natural self-logging point. Any per-token history must be driven by the orchestrator.

**The ensemble runner does not exist in the engine.** `demo/bd_acquisition/analysis.jl` hand-rolls the whole thing: `ensemble(build_and_run; root_seed, nseed) = [metrics(build_and_run(hash((root_seed,k)))) for k in 1:nseed]`, then `mean_rnpv`/`sem_rnpv`/`treatment_effect` over the result vector. AA offers no help here — `simulate` is single-agent (`interface.jl:160`), and `objective` (`utils.jl:67`) only wraps one `reinit!`+`simulate`. The per-member seed idiom `hash((root_seed,k))` is exactly CONTRACT §4 D8 (per-trajectory seeding); the demo proves the PATTERN but ships no reusable API.

**No results serializer.** ADR 0005 serializes the MODEL (`to_json_model`/`from_json_model`, `src/serialize.jl`); ADR 0007 `dump_state`/`restore` serializes a resumable STATE checkpoint. Neither emits a trajectory/ledger/ensemble for downstream analysis. CONTRACT §8.5 already MANDATES Arrow outputs ("Outputs MUST be Arrow … NOT JLD2; layout `runs/<model_hash>/<seed>/{trajectory.arrow, ledger.arrow, run.json}`") but nothing implements it.

So the work is one observability layer in three additive pieces, none of which touches the §1–§9 dynamics.

## Decision

### (A) The per-token trajectory log — orchestrator-driven, columnar, per-kind hook

**1. The logging hook (per kind, returns data — does not own storage).** A generic

```julia
log_token_fields(tok::AbstractStructuredToken)::NamedTuple = (;)   # default: log nothing
```

that a host kind overrides to declare WHICH fields to record (e.g. `log_token_fields(t::ProjectToken) = (; t.phase, t.npv_peak, t.pos_remaining)`). This is the maintainer's "tokens implement a logging method," but it returns the snapshot rather than holding it — keeping storage central (B) and the hook a pure 𝓕ₜ-measurable read. Opting in is per-kind and field-list-bounded, so the log does not grow unboundedly by default (load-bearing because retired tokens are KEPT under the Milestone-1 soft-`:removed` decision, PHASE0_REVIEW §5b).

**2. The store — shared columnar buffer on the problem, mirroring the per-program ledger row.** A new `state` field `token_trajectory::Vector{Tuple}` (sibling of `log`, `state.jl:80`); each tick appends `(t, token_name, fields::NamedTuple)` for every active token whose kind opts in, iterated in `token_sortkey` order so the rows are byte-reproducible under `(model, seed)` (§4 D4). This is a deliberate GENERALIZATION of `push_program_ledger_row!` (`ledger.jl:185-197`), which already snapshots `Dict(token_name => (cost,reward,valuation))` every tick in that exact order — the trajectory log does the same for declared attributes instead of the financial triple.

**3. The insertion point — one new tick step.** Add `push_token_trajectory_row!(state)` to `_step!` immediately after `push_program_ledger_row!` (`solvers.jl:1037`) and before the clock advance (`:1039`). At that seam all physics for the tick is done (evolve/finish/rules, `:1013-1022`), tokens are in their final positions, costs/rewards/valuations are attributed, and the timestamp is still this tick's `t` — the same seam, and the same determinism guarantees, the per-program row already relies on.

**4. The read API.** `token_trajectory(state) → DataFrame` (long form: `t, program, species, <field>…`) and `token_trajectory(state, name) → DataFrame` (one token's life). A `TokenPredicate` (ADR 0008) optionally scopes it — `token_trajectory(state, @select(Project, phase==:Phase3))` — reusing the §9.5 selection machinery rather than a new filter.

**5. "Typical" trajectory helpers — analysis ON TOP of the store, two well-defined senses.** `typical_trajectory` is ambiguous, so we ship both: (i) the MEDOID path — `representative_token(state[, pred]; metric)` returns the single token whose attribute path is closest to the per-cohort mean (answers "show me a typical program's life"); (ii) the ENVELOPE — `trajectory_envelope(state[, pred]; align_on)` aligns tokens by a chosen event (e.g. phase-entry time) and returns median + IQR bands per field (answers "typical ± spread"; this is also the single-run input to the ensemble band, recipe in ADR 0014). Both are pure post-processing over (4); neither adds engine state.

### (B) The ensemble runner — a function for the fan-out, `EnsembleProblem` as the AA-readable result

**Maintainer's question answered directly: build it in RD on AA's primitives; do NOT modify AA upstream, and do NOT route through AA's single-agent `simulate`.** AA has no ensemble (verified), and `objective`/`simulate` are single-agent; encoding RD's per-member seeding, ledger aggregation, and token-cohort statistics into AA would be the wrong layer. Instead:

**1. The runner (the fan-out).** A plain RD function

```julia
ensemble(build; nseed, root_seed = 2026, max_t, parallel = false) -> EnsembleProblem
```

where `build(seed) -> ReactionNetworkProblem` constructs ONE seeded member (the demo's `build_and_run` closure, promoted). Member `k ∈ 1:nseed` is seeded `hash((root_seed, k))` (§4 D8) and run to `max_t`. Members are INDEPENDENT and each owns its own `state.rng` (`state.jl:91`) — there is no shared global RNG — so the result is order-independent and `parallel=true` (threads/`Distributed`) is safe and `parallel=false` is the default. This subsumes `demo/.../analysis.jl`'s `ensemble`.

**2. `EnsembleProblem <: AbstractAlgebraicAgent` — the result is itself a hierarchy node.** A `FreeAgent`-style container whose `inners` are the member `ReactionNetworkProblem`s (entangled, `paths.jl`). Because it implements the ADR 0012 read surface — `observables(ens)` lists the exported aggregates, `getobservable(ens, name)` returns the cross-run reduction (mean/median/quantile of a per-run metric or of a species at a time) — an ensemble plugs into a larger AA hierarchy and into ADR 0014's `_draw` with NO new framework code. This is the "implement as an interface method within AA" instinct, done the additive way: we implement AA's METHODS on an RD type, we don't extend AA's source.

**3. Statistics.** `summarize(ens, run -> metric) -> NamedTuple` (mean, sem, quantiles over the per-run scalar) and `treatment_effect(ens_baseline, ens_deal; metric)` (the unpaired Δ with `se = sqrt(var(b)/nb + var(d)/nd)`, promoting `treatment_effect` from the demo) — the A/B lever comparison that drove the BD Δ-rNPV. Ledger statistics are `summarize(ens, p -> last(program_ledger(p).valuation))` etc.; the token-cohort statistics are `trajectory_envelope` (A5) lifted across members.

**4. Member production — two modes, both now shipped.** (a) REBUILD-per-seed (`mode = :rebuild`, default): `build(seed)` constructs a fresh problem per member — robust because the structured-token population is re-instantiated cleanly from the declarative `population[]` (ADR 0007 §B). (b) REINIT-and-reseed (`mode = :reinit`): build ONE member, then reinit-reseed and re-simulate that same problem for each subsequent seed — cheaper (reuses compiled closures + allocated store), enabled once ADR 0007 §D's `_reinit!` completion (RNG/counter/population restore) closed its gate. The reseed is a `seed` kwarg on `reinit!`/`_reinit!` that installs `Xoshiro(seed)` (re-snapshotting `initial_rng`, updating the realized `seed`) BEFORE `instantiate_population!` re-samples the t=0 marking — so a reinit-reseeded member's stream AND seed-sampled initial attributes match a fresh `build(seed)`, making mode (b) member-for-member equivalent to mode (a) (the acceptance gate). A faithful `deepcopy` snapshot of each finished run is retained, so `ens.members` still holds `nseed` independent `ReactionNetworkProblem`s (the read surface + any `metric(member)` unchanged); the reused problem is reinit-reseeded onward. **Precondition (documented, not auto-detected):** mode (b) is a legal substitute only for structurally HOMOGENEOUS members — a `build` that branches structurally on its seed must use `:rebuild`. `ens.mode` records which mode ran so a coupled reinit is never silently assumed.

### (C) The export bundle — format per artifact, dependency-tiered

The artifacts have DIFFERENT shapes, so "one format" is wrong; match each:

| Artifact | Shape | Format |
|---|---|---|
| `state.sol` trajectory | rectangular, all-Float64 | CSV (human) **+** Arrow (faithful) |
| `program_ledger(state)` | rectangular DataFrame | CSV + Arrow |
| ensemble summary (per-run metrics) | rectangular | CSV |
| `state.log` event stream | heterogeneous tuple-per-tick | **JSON** |
| `token_trajectory` (A) | semi-structured (fields vary by kind) | **JSON** (+ CSV when a single kind ⇒ rectangular) |
| run manifest (model hash, `seed`, RNG provenance, `tspan`, schema) | nested | **JSON** |

**1. `export_run(state, dir)`** writes a directory bundle refining CONTRACT §8.5: `run.json` (provenance + index), `trajectory.{csv,arrow}`, `ledger.{csv,arrow}`, `events.json` (the log), `tokens.json` (per-token histories). **`export_ensemble(ens, dir)`** writes one subdir per member plus a top-level `ensemble.json` (per-member seeds + the `summarize` table) — the `runs/<model_hash>/<seed>/…` layout §8.5 specifies.

**2. Dependency tiering — anticipate the ADR 0005 minimalism.** ADR 0005 PLANS to drop the TOML/CSV/JLD2 zoo, but on `ref-agents` today `CSV`, `JSON`, `JLD2`, `TOML` are all still in `Project.toml` (the drop is not yet implemented). So: JSON is the ALWAYS-AVAILABLE faithful format (JSON.jl is already a dep, used by `serialize.jl`; reuse its Dict-encoding pattern for the non-rectangular streams and the manifest); CSV via the already-present `CSV.jl` dep (no NEW dep — and it survives the ADR 0005 cull as the human-readable rectangular format §8.5 keeps); **Arrow lives behind a package extension/weakdep (`RDArrowExt`)** so the core stays lean and Arrow loads only when the user wants the faithful columnar form. `events.json`/`tokens.json` round-trip-test like the model JSON (the symmetry with ADR 0005's `to_json_model` ⟷ `from_json` test).

## Consequences

- The three maintainer asks are met additively: per-token time-series (A) with two precise "typical" notions (A5), an ensemble runner + cross-run statistics (B) that is itself an AA node (B2), and a results export bundle (C) — none touching §1–§9 dynamics (the trajectory log is one read-only tick step; the ensemble is a fan-out over existing `simulate`; export reads finished state).
- The per-token log GENERALIZES the per-program ledger row rather than inventing a parallel mechanism — same seam (`solvers.jl:1037`), same `token_sortkey` order, same `(t, name, payload)` shape — so determinism (§4 D4) and the retired-token semantics carry over for free.
- `EnsembleProblem`-as-AA-node means an ensemble composes with ADR 0012 coupling and ADR 0014 plotting with no new framework surface — `getobservable(ens, "mean_rnpv")` is wireable into a reporting agent, `draw(ens)` plots the distribution.
- Costs: one `state` field (`token_trajectory`) + one tick step (`push_token_trajectory_row!`) + the `log_token_fields` hook (A); the `ensemble`/`summarize`/`treatment_effect` functions + the `EnsembleProblem` type implementing the ADR 0012 read surface (B); the `export_run`/`export_ensemble` writers + the `RDArrowExt` extension (C). (Historical: mode (b) was originally gated on ADR 0007 §D; that gate is now CLOSED and mode (b) has shipped — see the Status line.)
- One semantic commitment: a token's logged row is its state at the END of the tick (post-rules, pre-clock-advance), matching the per-program ledger's observation point — NOT a within-tick snapshot. A consumer wanting bind-time vs finish-time deltas reads `past_bonds`, not the trajectory log.

## North-star tie-in (BD)

The trajectory log turns the BD demo's post-hoc reconstruction into first-class data: each `ProjectToken`'s `phase`/`npv_peak`/`pos_remaining` is recorded every tick, so `trajectory_envelope(state, @select(Project, therapeutic_area==:onc))` shows the typical onc-program lifecycle and `representative_token` picks the medoid program to narrate. `ensemble(build_pipeline_run; nseed=160, root_seed=2026)` reproduces the demo's 160-seed run as a one-liner; `treatment_effect(ensemble(baseline), ensemble(deal))` IS the Δ-rNPV ± SE the BRIEF reports (subsuming `analysis.jl`). `export_ensemble(ens, "runs/")` then dumps the trajectory/ledger/manifest bundle the figures (ADR 0014) and the presentation read from — closing the loop from run → statistics → export → plot without bespoke demo code.

## Invariants

1. **Trajectory determinism.** `token_trajectory` rows are appended in `token_sortkey` (species, creation_index, uuid) order each tick (`predicates.jl:105`); `(model, seed)` fully determines the log (§4 D4). The logging hook is 𝓕ₜ-measurable (a pure field read, no RNG, no future).
2. **Bounded by opt-in.** A kind logs only the fields its `log_token_fields` returns (default: none); the trajectory log never grows for kinds that don't opt in.
3. **Ensemble independence.** Each member owns its `state.rng` seeded `hash((root_seed,k))`; results are order- and parallelism-independent; `(root_seed, nseed, build)` determines the ensemble (§4 D8/D9).
4. **EnsembleProblem is a readable node.** `getobservable(ens, name)`/`observables(ens)` resolve for every exported aggregate (ADR 0012 invariant 1); an unknown name is a diagnostic, never AA's silent `@error`.
5. **Export fidelity.** Rectangular artifacts round-trip through Arrow byte-faithfully; the JSON streams round-trip structurally (the §8 round-trip guarantee, ADR 0005 symmetry). The manifest pins `(model_hash, seed)` so a bundle is traceable to a replayable run (§4 D6).
6. **Read-only.** Nothing in (A)/(B)/(C) mutates dynamics: the trajectory step only reads + appends, the ensemble only constructs + steps existing problems, export only reads finished state.

## Open questions

- **Trajectory log cardinality / streaming.** For a long run with many tokens × many ticks the in-memory `token_trajectory` is O(#ticks × #active tokens × #fields). Lean: keep in-memory for Milestone 1 (mirrors the per-program ledger's own O(#ticks × #tokens) row growth, accepted in PHASE0_REVIEW §5b), with an optional `every::Int` decimation kwarg and an `export`-as-you-go streaming sink as future work if a real run bites. Flag any decimation in `run.json` so a thinned trajectory never reads as full-resolution.
- **`representative_token` metric.** The medoid needs a path metric over heterogeneous fields (Symbol `phase` vs Float64 `npv_peak`). Lean: per-field normalized distance with a kind-supplied weight vector (default uniform over the logged fields), documented as a heuristic, not a canonical "typical."
- **Ensemble member retention.** Holding all `nseed` finished problems as `inners` is memory-heavy for large ensembles. Decide whether `EnsembleProblem` retains full member states (needed for `trajectory_envelope` across runs) or only the extracted per-run metrics + a re-runnable `(build, seed)` to lazily reconstruct. Lean: retain metrics + seeds eagerly, full states opt-in (`keep_members=true`), since most statistics need only the per-run scalars.
- **`export_ensemble` size.** A 160-member bundle with full trajectory + token logs is large. Decide the default export granularity (summary-only vs per-member full) and whether Arrow compression is on by default in `RDArrowExt`.
- **Interaction with ADR 0012 coupling.** A coupled member (RD inside a larger AA hierarchy) is driven by `simulate(root)`, not `simulate(rd)` (§13.1). Confirm `ensemble` can take a `build(seed) -> root` that returns the HIERARCHY root and still extract the RD child's trajectory/ledger for aggregation; document the `getagent(root, "rd")` extraction path.
