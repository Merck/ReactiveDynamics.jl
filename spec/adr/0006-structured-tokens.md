# ADR 0006 — Structured/agentic tokens: live instantiation, construction, queries; and the custom-function boundary (post-`@register`)

- Status: Accepted — maintainer-required, 2026-06-20. Structured/agentic tokens are crucial: in the Business-Development north-star a PROJECT is a structured entity (an agent with attributes, custom behavior, and history), and the engine must support, DURING simulation, (a) instantiating new structured-token instances, (b) their construction, and (c) querying them. This ADR pins the contract that makes that sound.
- Verification note: an adversarial pass confirmed (against source on Julia 1.12.5) that this design is eval-safe and append-only-safe, and that all five cited token-path bugs are real (`src/solvers.jl:288,452,455,476,512`). It flagged the CURRENT engine as non-deterministic / D4-inconsistent because token iteration today is raw `Dict`-value order (`inners::Dict{String,…}`, `AlgebraicAgents.jl/src/interface.jl:12`); §(E) and Invariant 5 of this ADR are precisely the fix — impose a `(species, name, uuid)` total order before any order-bearing use — so the design is deterministic by construction, and those flags describe the behavior being corrected, not this ADR.
- Relates to: ADR 0001 (native `ReactionNetworkProblem` engine, single clock, `_step!` at `src/solvers.jl:642`), ADR 0002 (priority-weighted progressive-filling allocation — the order in which tokens bind), ADR 0003 (dependency-free typed struct-of-columns IR; the `specStructured` flag and a promoted reactant relation live in that store), ADR 0004 (runtime mutation = append-only + soft-deactivate; the frozen construction-time varmap), ADR 0005 (eval-free single-JSON + typed `ExprNode` IR; `OP_WHITELIST`/`DIST_WHITELIST`, action statements `{SetSpecies, SetParams, Log, Seq}`). This ADR answers maintainer ruling 2 (post-`@register` custom functions), ruling 3 (action statements are enough for now), and ruling 4 (species KINDS a priori, structured INSTANCES live).

## Context

ReactiveDynamics is a timed, stochastic, resource-constrained GSPN / discrete-event engine for modeling business/R&D processes. ADRs 0001–0005 fix the engine, allocator, store, mutation contract, and serialization. What remains unspecified is the structured-token story end to end: how an agentic token TYPE and its CONSTRUCTOR are defined now that we are removing module-scope `eval` (`@register`, `src/interface/update.jl:513`), how a token INSTANCE is added and retired live, and how rates, actions, and the host program QUERY the live token population — all without re-opening the import-time RCE that ADR 0005 designed out.

Ground-truth facts, verified against source on branch `ref-agents`:

- A structured token is an AlgebraicAgents (AA) agent: `AbstractStructuredToken <: AbstractAlgebraicAgent` (`src/interface/agents.jl:6`); the default `BaseStructuredToken` is `@aagent FreeAgent` with protocol fields `species::Union{Nothing,Symbol}`, `bound_transition::Union{Nothing,Transition}`, `past_bonds::Vector{Tuple{Symbol,Float64,Transition}}` (`src/interface/agents.jl:11-15`), plus AA's injected `uuid`/`name`/`parent`/`inners`/`relpathrefs`/`opera`.
- Token INSTANCES are NOT positional `state.u` columns. They live as AA inner agents under a single `FreeAgent("structured")` container entangled once at construction (`src/solvers.jl:612`), keyed in the container's `inners` dict by `getname` (`AlgebraicAgents.jl/src/paths.jl:116`). The structured-species columns of `state.u` are a DERIVED VIEW: `update_u_structured!` (`src/solvers.jl:630-639`) sets `state.u[i] = count(a -> get_species(a) == species && !isblocked(a), structured_tokens)` for each `specStructured` species, called four times per `_step!` (`src/solvers.jl:643,649,653,655`) around every mutating phase.
- A token instance is added live by `add_structured_token!(problem, agent) = entangle!(getagent(problem,"structured"), agent)` (`src/interface/agents.jl:42-44`). `entangle!` (`AlgebraicAgents.jl/src/paths.jl:114-123`) only `setparent!`s, `push!`es `getname(agent) => agent` into `inners`, and syncs directory/opera — it never reads or writes `state.u` and never shifts a species index. `disentangle!` (`AlgebraicAgents.jl/src/paths.jl:135-174`) is equally `state.u`-inert.
- Token TYPES and CONSTRUCTORS are defined two `eval`-based ways today. `@structured_token network struct M1 ...` calls `AlgebraicAgents.aagent(BaseStructuredToken, AbstractStructuredToken, type, ReactiveDynamics)` (`src/interface/agents.jl:30-39`), whose worker `define_agent` runs `Base.eval(__module, struct_expr)` with `__module = ReactiveDynamics` (`AlgebraicAgents.jl/src/agents.jl:48`). The raw `@aagent BaseStructuredToken AbstractStructuredToken struct M2` wrapped in `@register` (`tutorial/agents-integration/agents.jl:90-93`) lands in RD the same way, since `@register = @eval ReactiveDynamics` (`src/interface/update.jl:513`). Constructors `ReactiveDynamics.M1(time, descriptor)` (`tutorial/agents-integration/agents.jl:68-70`) and custom behavior funcs `update_prob_transition`/`f_species` (`tutorial/agents-integration/agents.jl:74-84`) are `@register`'d into RD too.
- The ONLY reason the type/constructor had to live in RD is a name-resolution artifact: a structured RHS `@structured(M1(@t(), rand(4)))` (`tutorial/agents-integration/agents.jl:27`) is handled by `structured_rhs` (`src/solvers.jl:333-397`), which `context_eval`s `state.wrap_fun(expr)`; `wrap_expr` `eval`s that closure inside the RD module (`src/compilers.jl:122-126`) and `context_eval` `Base.invokelatest`s it (`src/state.jl:68`), so a bare symbol `M1` resolves against RD's namespace. Nothing semantic requires the type to be in RD.
- Registering a structured KIND is already `eval`-free: `register_structured_species!(net, type)` only `add_part!`s the species and flips `specStructured = true` (`src/interface/agents.jl:18-27`); `structured_token_names` is captured at construction (`src/solvers.jl:556-557`).
- Allocation iterates `structured_token = collect(values(inners(getagent(state,"structured"))))` (`src/solvers.jl:173`), filters `get_species == type && !isblocked` (`src/solvers.jl:202-205`), and `sort!`s by `priority(a, transName)` descending (`src/solvers.jl:207-211`, ongoing pass `:274-283`). `priority` defaults to `0.0` (`src/interface/agents.jl:67`). `isblocked(a) = !isnothing(get_bound_transition(a))` (`src/interface/agents.jl:53`).
- The token protocol the engine relies on: `get_species`/`set_species!` (`src/interface/agents.jl:70-71`), `get_bound_transition`/`set_bound_transition!` (`src/interface/agents.jl:61-64`), `isblocked` (`:53`), `add_to_log!` → `past_bonds` (`:56-58`), `priority` (`:67`); tokens are clock-inert (`_step!`/`_projected_to` no-ops, `:49-50`).
- Known engine defects on the token path, all confirmed: `set_bound_transition!` is mis-called with the `.bound_transition` FIELD instead of the token agent at `src/solvers.jl:288` (ongoing-alloc) and `:452, :476` (finish! unbind) — since the setter is `set_bound_transition!(a::AbstractStructuredToken, t)` (`src/interface/agents.jl:62`), this MethodErrors (it does not silently no-op); correct form is at `:215, :489`. `delete!(vector, index)` at `src/solvers.jl:455` is not positional removal for a `Vector` and MethodErrors — must be `deleteat!` (cf. correct `:479, :383`). `free_blocked_species!` references an undefined `q` at `src/solvers.jl:512`. The event channel is a no-op: `event_action!` fetches `:eventAction` but never evaluates it (`src/solvers.jl:323`).
- Queries are ad hoc today: `collect(values(inners(getagent(network_instance,"structured"))))` (`tutorial/agents-integration/agents.jl:116`). AA provides `getagent` glob/regex paths (`AlgebraicAgents.jl/src/paths.jl:2,46,80`), `@filter` + `Base.filter(agent, query)` (`AlgebraicAgents.jl/src/queries.jl:48,59,83`), `getobservable`, and wires.

## Decision

### (A) Plain species vs. structured species — two kinds, one store

A PLAIN species is a `Float64` count in a fixed `state.u` column. It is defined a priori, and its index is governed by ADR 0004: existing indices never move; appending a new plain species is index-safe only because the construction-frozen varmap (`src/compilers.jl:149`, baked into closures at `:110`) hard-codes `state.u[i]` positions for existing plain species.

A STRUCTURED species is a KIND (`specStructured = true`, `src/interface/agents.jl:24`) whose INSTANCES are live AA agents under the `"structured"` container. Its `state.u` column is NOT authoritative storage; it is a reflected count recomputed every tick by `update_u_structured!` (`src/solvers.jl:630-639`). The single source of truth for a structured species is the set of live unblocked inner agents of that kind. KINDS are defined a priori (maintainer ruling 4 — no live species-kind retirement). Only structured-token INSTANCES are added/removed live.

This split is what makes live instantiation safe: a structured instance never occupies a positional slot, so it cannot collide with the frozen plain-species varmap.

### (B) A token TYPE and CONSTRUCTOR are HOST JULIA CODE, not serializable data — the eval-free boundary

We draw a hard line between two categories that `@register` conflated:

- HOST-JULIA side (trusted, compiled in the user's own package by the normal Julia compiler, NEVER serialized, NEVER reconstructed from a file): structured-token TYPES (`struct ProjectToken <: ReactiveDynamics.AbstractStructuredToken`), their CONSTRUCTORS (`ProjectToken(time, descriptor) = ...`), custom protocol-method overrides (`priority`, `get_species`, ...), and any genuinely-algorithmic custom behavior function.
- SERIALIZABLE-DATA side (the `model.rdj.json`, inert, untrusted, eval-free per ADR 0005): WHICH kinds a model uses — by NAME only, as a string matched against a host-populated registry; `ExprNode` rate/stoich/cycletime/cost trees; action-statement bodies; and the structured-RHS construction/move nodes that REFERENCE a kind by name. A JSON model can say "spawn a token of kind `ProjectToken` with these arg-expressions" but can NEVER define `ProjectToken` or carry Julia source for it.

This is not a re-opening of the ADR 0005 RCE. ADR 0005 closes `eval` of BYTES READ FROM A FILE (`src/loadsave.jl:65,72`; the `Base.convert` hooks at `src/ReactiveDynamics.jl:99,101,102`). A `struct` the user writes in their own package is host program text compiled by Julia — categorically distinct from untrusted file bytes. The registry indirection means the only thing the data file controls is a lookup KEY into a table the host program populated, which is precisely the closed-whitelist discipline ADR 0005 already uses for `OP_WHITELIST`/`DIST_WHITELIST`/`REF_KINDS` — here it is a host-extensible structured-kind/function registry.

Concretely, `@structured_token` is replaced by a hygienic macro that expands a normal field-inherited `mutable struct` AT THE USER CALL SITE (`esc`), carrying the `BaseStructuredToken` protocol fields (`src/interface/agents.jl:11-15`) plus the user's extras, with supertype `ReactiveDynamics.AbstractStructuredToken`. The struct lands in the USER's module, not RD. The token protocol is satisfied by the defaults on `AbstractStructuredToken` (`src/interface/agents.jl:49-71`); the user overrides `priority`/`get_species` as needed. Even the residual `Base.eval(__module, ...)` that AA's `define_agent` performs (`AlgebraicAgents.jl/src/agents.jl:48`) is a COMPILE-TIME macro expansion in the user's own module — exactly how `@kwdef` and every struct-defining macro work — not runtime eval of file bytes. If the maintainer wants literally zero `eval` even at macro expansion, the macro returns `esc(struct_expr)` directly and RD reimplements `define_agent`'s field-inheritance-from-base-type (`AlgebraicAgents.jl/src/agents.jl:22-32,41-48`); the user site must then have `AbstractStructuredToken`/`BaseStructuredToken` in scope (replace `using ReactiveDynamics: M1`, `tutorial/agents-integration/agents.jl:66`, with `import ReactiveDynamics: AbstractStructuredToken, BaseStructuredToken`).

### (C) A per-network function/kind REGISTRY replaces `@register`

Why custom functions had to live in RD's module scope (the constraint we are removing): the compiler never substitutes a CALL HEAD. `recursively_substitute_vars!` (`src/compilers.jl:28-44`) rewrites only leaf symbols that are species/param names (→ `state.u[i]`/`state.p[:x]`); a custom call like `α(candidate_compound, …)` keeps `α` as a BARE symbol in `ex.args[1]`. `wrap_expr` then `eval`s the closure inside the `ReactiveDynamics` module (`src/compilers.jl:122-126`), so at run time that bare `α` resolves as `ReactiveDynamics.α` — which is the entire reason `@register` does `@eval ReactiveDynamics $ex` (`src/interface/update.jl:513`) and why `context_eval` needs `Base.invokelatest` to dodge the world-age bump from that runtime eval (`src/state.jl:68`). The constraint is a name-resolution artifact, not anything semantic. The registry dissolves it: resolution moves from a MODULE GLOBAL to a DICTIONARY KEY, so a custom function never needs to live in RD, nothing is eval'd into RD's namespace, and (because the function is pre-compiled, not runtime-eval'd) the world-age problem and the `invokelatest` indirection (`src/state.jl:68`) both go away — a correctness and a performance win.

Custom functions are supplied as ORDINARY Julia functions the host writes and compiles normally, then registers BY NAME into a per-network registry. Add one field to `@aagent struct ReactionNetworkProblem` (`src/state.jl:40-63`, beside `wrap_fun::Any` at `:61`):

```julia
registry::Dict{Symbol, Any}   # host-supplied functions AND structured-kind constructors/types, keyed by name
```

populated from the host program (never from a file):

```julia
prob = from_json("pipeline.rdj.json"; registry = Dict(
    :pos_curve              => (state, transition) -> 0.6,    # custom prob-of-success helper
    :update_prob_transition => update_prob_transition,        # token behavior, defined normally
    :ProjectToken           => ProjectToken,                  # structured-kind constructor
))
```

`Call{op, args}` resolution in `to_expr` (ADR 0005) becomes a TWO-TIER closed allow-list checked at BUILD time inside `validate`/`build_store`:

1. BUILTINS — `op ∈ OP_WHITELIST` (and `Sample{dist}` with `dist ∈ DIST_WHITELIST`): lowered INLINE to the literal builtin call, exactly as today, package-fixed, registry untouched.
2. USER NAMES — `op ∉ OP_WHITELIST` but `op ∈ keys(registry)`: lowered to a registry lookup-and-apply (e.g. `:(registry[:pos_curve](state, transition))` for a behavior fn, or `:(registry[:my_rate](<lowered args>))` for a value helper), captured at build so the compile-once property of `wrap_fun` (`src/compilers.jl:122-126`) holds.
3. NEITHER → `validate` REJECTS with a diagnostic ("unknown operator/function `op`: not a builtin and not in the network registry").

Because builtins lower inline with positional value-args while behavior fns are called `(state, transition)` (`src/state.jl:68`) and scalar helpers take value-args, each registered name carries a small calling-convention tag (value-args vs `(state, transition)`) so `to_expr` lowers it unambiguously. The JSON stays eval-free and unchanged in shape — it carries only the NAME — and `validate(spec; registry_names)` treats the registry key set as the closed EXTENSION of the allow-list. The trust boundary is the host program that populated the registry, not the file; the file alone remains inert.

Each former `@register` use maps cleanly: rate/observable helpers (`bool_cond`, `tdecay`, `src/interface/update.jl:509-510`) become `Call{:name, ...}` ExprNodes resolved through the registry; the body of `update_prob_transition` (`tutorial/agents-integration/agents.jl:79` sets `transition[:transProbOfSuccess]`) is a single attribute write, i.e. an ADR 0005 `SetParams` action statement, and needs no host code at all (maintainer ruling 3); genuinely-imperative behavior or routing (`f_species`) becomes either a protocol-method override on the token type or a registry-named callee; arbitrary registered bodies that fit neither are DROPPED (ADR 0005 Consequences).

### (D) Live instantiation lifecycle — append-only-safe via `entangle!`

A structured-token instance is added live at a TICK BOUNDARY (between `_step!` calls, per ADR 0004) by `add_structured_token!(problem, agent)` = `entangle!(getagent(problem,"structured"), agent)` (`src/interface/agents.jl:42-44`), or mid-RHS by `structured_rhs` (`src/solvers.jl:333-397`) for `@structured(...)`. This is APPEND-ONLY-SAFE and does NOT touch the ADR 0004 frozen varmap: `entangle!` (`AlgebraicAgents.jl/src/paths.jl:114-123`) only mutates the `inners` dict + AA bookkeeping; the structured `state.u[i]` is recomputed from the live count by `update_u_structured!` (`src/solvers.jl:630-639`), with `i` taken from a runtime `enumerate` over `state.acs[:,:specName]` (`src/solvers.jl:632`), never from a frozen closure. The frozen varmap (`src/compilers.jl:149,132,110`) freezes only PLAIN-species positions, which structured instances never occupy. The lever does NOT use the event channel, which is a no-op (`src/solvers.jl:323`).

The five-phase lifecycle is fully specifiable on the existing protocol:

1. Instantiate (`entangle`) — pre-sim via `add_structured_token!` (`tutorial/agents-integration/agents.jl:108-109`) or mid-sim via `structured_rhs` (`src/solvers.jl:333-359` for `@structured`).
2. Bind as a resource — priority-ordered allocation in `evolve!`: `filter(get_species == type && !isblocked)` (`src/solvers.jl:202-205`), `sort!` by `priority` (`:207-211`), `set_bound_transition!(token, transition)` (`:215`). A bound token `isblocked` and so drops out of BOTH later allocation filters and the reflected count for the bond's duration. Structured species cannot use modality `:rate` (`src/solvers.jl:38-42`) and require integer stoichiometry (`:196-200,268-272`).
3. Move (place transition) — `@move(:from,:to)` (`src/solvers.jl:360-389`) re-uses the SAME token object via `set_species!(token, to)` (`:378`) then `set_bound_transition!(token, nothing)` (`:384`), preserving identity and `past_bonds` history across phases. (The redundant `entangle!` of an already-inner token at `src/solvers.jl:376` should be DROPPED — it re-runs `setparent!`/`push!` idempotently for a stable name, but desyncs if the name-uniqueness fix below changes a token's key; it is never needed since the token is already inner.)
4. Unbind on completion — `set_bound_transition!(..., nothing)` and removal from `bound_/nonblock_structured_agents` in `finish!` (`src/solvers.jl:443-481`) and `free_blocked_species!` (`:510-522`).
5. Retire — SOFT by default: `set_species!(agent, :removed)` (`src/solvers.jl:488`) keeps the token a queryable inner agent (preserving its `past_bonds` audit trail) but, because `:removed` matches no active kind, it is no longer counted by `update_u_structured!` nor selected by any allocation filter. HARD: `disentangle!` (`AlgebraicAgents.jl/src/paths.jl:135-174`) reclaims memory and is equally index-safe; offer it for long BD runs whose retired-token history is no longer needed.

Note: `finish!` also does an immediate `state.u[i] += 1` per RHS-spawned token (`src/solvers.jl:425`), which the next `update_u_structured!` (`src/solvers.jl:655`) overwrites with the recomputed count. The freshly-entangled token is unbound, so the reflected count picks it up; the `+= 1` is redundant/dead for the structured column and should be removed to avoid misleading log consumers.

### (E) The query API — deterministic accessors on AA primitives

The query surface (e.g. `src/interface/queries.jl`) builds on AA primitives but imposes a TOTAL ORDER before returning any sequence, because AA's `inners` is a plain `Dict{String,AbstractAlgebraicAgent}` (`AlgebraicAgents.jl/src/interface.jl:80`, allocated `agents.jl:135`) and `Base.filter`/`@filter` reorder through a freshly-built `Dict` in `flatten_hierarchy` (`AlgebraicAgents.jl/src/queries.jl:84`, `utils.jl:45-53`). Julia `Dict` iteration order is hash/rehash-dependent, NOT insertion-stable, which CONTRACT D4 (`docs/CONTRACT_DRAFT.md:281`, "iterate in index order, never Dict/Set insertion order") forbids for any order-bearing consumer. `_filter` additionally swallows every predicate error as `false` (`AlgebraicAgents.jl/src/queries.jl:107-113`), so a typo degrades to silent zero matches.

The surface:

- `tokens(problem[, species])` — deterministic snapshot, `sort!`ed by `token_sortkey(a) = (something(get_species(a), :_), getname(a), string(getuuid(a)))`. This is the single chokepoint where AA Dict order is erased; every other accessor composes it.
- `active(...)`/`blocked(...)` — built on `isblocked` (`src/interface/agents.jl:53`); `length(active(problem, s))` equals the engine's reflected `state.u` entry (`src/solvers.jl:632-636`), an assertable invariant.
- `tokenattr(a, field, default=missing)` — `hasproperty`-guarded attribute read over BD fields (`descriptor`, `time_created`, and BD extensions `phase`/`budget`/`npv`); avoids `_filter`'s silent swallow.
- `ntokens`/`nactive`/`sumattr`/`maxby`/`nbound` — reductions over the ORDERED `tokens(...)` vector, so float-reduction order and `argmax` ties are deterministic; `nbound` uses `get_bound_transition` (`src/interface/agents.jl:61`).

A rate/action that must read the sibling pool (e.g. "number of active phase-2 projects") does so via a NEW closed ExprNode `TokenAgg{reducer ∈ (:count,:sum,:max), species, field, active_only}`, lowered by `to_expr` to the reductions above (the compiled closure receives `(state, transition)` and `state` is the problem, so `getagent(state,"structured")` resolves — the same call the solver makes at `src/solvers.jl:342`). This keeps the authoring boundary eval-free (a tagged node from a closed enum, exactly the ADR 0005 contract) and is the ONLY sanctioned way a rate queries tokens — never an arbitrary registered function. `getobservable` on the structured container is currently unimplemented (`AlgebraicAgents.jl/src/interface.jl:299-301` returns `@error`); implement it to surface the same aggregates as named AA observables, giving coupled agents a `wires`-reachable read path that respects the ordering layer.

### (F) Disposition of `@register` / `@structured_token`

- `@register` (`src/interface/update.jl:513`) and the file-loaded `registered` eval block (`src/loadsave.jl:72`) are REMOVED as model-authoring paths. Optionally keep a thin HOST-SCOPE helper `register!(prob, :name, fn)` that is sugar over `prob.registry[:name] = fn` — it takes a live `Function`/type value the caller already compiled, never source, and is never reachable from `loadsave.jl`.
- `@structured_token` keeps its NAME but expands hygienically at the user call site (the struct lands in the user module, not RD), as in (B). The raw `@aagent ... struct M2` inside `@register` migrates to the same form, dropping the `@register` wrapper.
- Hard rule: the loader never receives, parses, or evals function source; the only Julia source ever produced is `to_expr` over the closed allow-list extended by the registry key set.

## Consequences

- Structured tokens become a first-class, contractually-specified mechanism: live instantiation, identity-preserving phase movement, soft/hard retirement, and a deterministic query API, all on the existing AA primitives.
- Live instantiation is provably index-safe: it is `entangle!`/`disentangle!` of an inner agent, never a `state.u` reindex, so it cannot break the ADR 0004 frozen-varmap invariant. Plain-species append rules and structured-instance append rules are now cleanly separated.
- No reintroduction of the ADR 0005 RCE: token types/constructors/behavior are host Julia compiled by the user's package; the JSON references kinds and functions by NAME against a host-populated registry; `validate` rejects any unregistered name. The file stays inert.
- The closed allow-list grows by exactly one well-defined axis (the per-network registry key set) and the IR grows by exactly one node (`TokenAgg`); both are additive, eval-free, and JSON-Schema-enumerable like `OP_WHITELIST`.
- Costs: this requires real engine work — the `structured_rhs` constructor resolution must move off `context_eval` of a bare RD symbol onto registry-by-name dispatch (a `Construct{kind, args}` node); the determinism fix (ordered/sorted token iteration) must be wired into allocation; and the confirmed token-binding bugs must be fixed in the same pass. Two models in one session can no longer clobber each other's behavior funcs (the per-network registry replaces last-write-wins `@eval ReactiveDynamics`), but the tutorial and any `@register`-using models are a breaking API change and must be rewritten.

## North-star tie-in (BD)

A PROJECT (acquisition target / R&D program) is a `ProjectToken <: AbstractStructuredToken` carrying `phase`, `npv_estimate`, `cost_to_date`, `pos_remaining`, `acquired`, `acq_time` plus the protocol fields, overriding `priority` so acquired late-stage programs win scarce scientists/budget at the genesis (`src/solvers.jl:207-211`) and ongoing (`:279-283`) binds. Pipeline phases `{:Discovery,:Phase1,:Phase2,:Phase3,:Market}` are a-priori structured KINDS (`register_structured_species!`); each advance is a transition consuming a project-in-phase-N token plus renewable resources (scientists `@conserved`, budget `@rate`) for a `cycletime`, emitting the program in phase N+1 via `@move(:PhaseN,:PhaseN1)` on `Binomial(q, PoS)` success (`src/solvers.jl:413`). The ACQUISITION LEVER fires at a tick boundary: `add_structured_token!(prob, ProjectToken(:Phase2, prob.t; acquired=true, ...))` injects NEW phase-2 targets mid-run with no index churn, optionally with `set_params` (`src/state.jl:246`) operational perturbations — NOT via the no-op event channel. rNPV is a query-reduction `sumattr(active(prob, :InFlight), ...)` of `pos_remaining · npv_estimate · discount(prob.t − acq_time) − cost_to_date`, netted against the engine ledger streams `:valuation`/`:valuation_cost`/`:valuation_reward` (`src/solvers.jl:659-666,308-311,505`), with `past_bonds` supplying realized phase history. Pre/post-acquisition rNPV is the diff between two SAME-SEEDED runs differing only by the lever (requires the CONTRACT §4 D5 RNG threading to isolate the lever's effect).

## Invariants

1. Exactly one species per token at a time: `species` is a single scalar field mutated atomically by `set_species!` (`src/interface/agents.jl:70-71`).
2. A bound token is `isblocked` (`src/interface/agents.jl:53`) and is excluded from BOTH re-allocation and the reflected count for the bond's duration.
3. The reflected structured count equals the number of live UNBLOCKED tokens of that kind: `length(active(prob, s)) == state.u[idx(s)]` after each `update_u_structured!`.
4. Live instantiation/retirement touches only the `inners` dict + AA bookkeeping, never `state.u` positions; the frozen varmap governs plain species only.
5. Token iteration that feeds allocation, an RNG draw, or a log entry is TOTALLY ORDERED before use — by `(species, name, uuid)`, never raw AA Dict order (CONTRACT D4). Equal-`priority` binding order is thereby deterministic across runs and insertion histories.
6. Token `inners` keys are unique: derive the key from the AA `uuid` (`getuuid`, `uuid4` at `AlgebraicAgents.jl/src/agents.jl:134`), not from `randstring(4)` names (`tutorial/agents-integration/agents.jl:69,96`) which can collide and silently evict a live token. The uuid doubles as the stable tie-break key for invariant 5.
7. Token TYPES/CONSTRUCTORS are host Julia; the JSON references them by name only; an unregistered name is a `validate()` diagnostic, never an eval.

## Resolved (maintainer, 2026-06-20)

- **Determinism source for the token sort-key → a per-species creation counter** (NOT the AA uuid threaded through the RNG). The k-th token instantiated of a given species gets a monotonic creation index k; the token sort-key (Invariant 5) becomes `(species, creation_index)`, which is reproducible without hijacking AA's uuid generation (which RD does not control). The uuid remains the token's identity (and the unique `inners` key, Invariant 6); the creation counter is purely the deterministic tie-break. The counter is part of the seeded run state, so `_reinit!` resets it (CONTRACT §4 D7).
- **Retired-token growth → accept for Milestone 1, with an escape hatch.** Soft-`:removed` retirement stays the DEFAULT (it preserves the `past_bonds` audit trail that rNPV/audit consumes), and `disentangle!` is offered as an explicit opt-out for callers who do not need retired-token history. The per-tick O(#tokens-ever-created) reflect/sort cost is accepted as-is; periodic archival to a side log is a future optimization to add ONLY if a real BD run shows it bites — no pre-optimization.
