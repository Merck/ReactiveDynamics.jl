ReactiveDynamics.jl  ·  the agentic layer — a capability overview

A skill layer that carries a business question to a defensible number

ReactiveDynamics.jl simulates timed, resource-constrained processes. The gap between owning that engine and answering a question with it is expert knowledge — the contract, the allocator semantics, the calibration discipline. This layer is that knowledge, made executable: four phases, five skills, one CLI, and a gate in the middle that is allowed to refuse.

A model here is inert data and the validator is a pure function — which is what makes an agent a safe author of one. Every model is a single JSON document whose expressions are node-tagged trees from a closed whitelist, never Meta.parsed and never evaled on load. ReactiveDynamics.validate(doc) is a static pass returning a vector of diagnostics with JSON paths, and from_json_model refuses to build anything it rejects. The engine's own source says what that is for: an LLM runs this to self-check a model before from_json. So the agent emits structured data, repairs against machine-readable paths, and — because (model, seed) determines a run contractually — every number it quotes replays exactly. The layer below is the trust boundary; the layer above is procedure.

What gates adoption of a simulation engine is rarely a missing feature. It is the distance between I have a decision to make and I have a model in which the scarce thing genuinely binds — and closing that distance takes knowledge spread across a normative contract, a stack of architecture decision records, and a calibration discipline that mostly lives in worked case studies. That is exactly the kind of knowledge an agent can carry.

So the claim of this layer is narrow and checkable: it turns a framework that requires an expert into one that requires a question. Four phases, each leaving an artifact on disk, each with a gate that has to clear before the next begins. The phases are the obvious part. The gates are the product.

This page is the capability first and the demonstration second — what it does, how it is built, what the integration surface is, how you drive it today. Then one full engagement-scale study, dialogue and commands and one retracted number included, with the briefing it produced attached in full at the end.

1 · What it does

Four phases. Each ends in an artifact on disk, and each has a gate that has to clear before the next begins.

PhaseSkillArtifactThe gate
1. FRAMErd-frameBRIEF.mdthe qualifying test — something binds, something takes time, something is decided mid-flight — plus pre-registered failure modes
2. AUTHORrd-authormodel.rdj.json, one per armrdx validate returns zero diagnostics
3. DIAGNOSErd-doctorDOCTOR.mdnine plausibility checks pass, or every failure is understood and written down
4. REPORTrd-reportFINDINGS.mdheadline, decision rule, caveats — and every number carrying a spread and a seed

The artifacts are the interface, not a byproduct of one. A study that dies mid-conversation resumes from its directory alone, and a number quoted six months later is traceable to the command that produced it.

The gate in the middle is the differentiator

validate proves a document is well-formed. It proves nothing about whether the model is about the user's system — and a schema-clean model can be confident nonsense. That is the failure mode of every LLM-authored simulation, and it is not detectable by any schema. So DIAGNOSE is a short seeded run followed by nine checks on what actually happened, each cross-examined against what the brief said was supposed to happen:

CheckWhat it catches
transitions_firea step that never fires once — an entire branch of the process silently missing
completions_existwork that starts and never finishes inside the horizon
contention_existsnothing ever ran out, so the marginal question is arithmetic and the engine added nothing
intended_resource_bindssomething binds, but not the thing the brief called scarce — the number answers a different question
modality_intenta resource the brief calls reusable, declared consumed; the commonest silent error, because consumed is the default
horizon_sufficientwork still in flight at the end — the number is truncated, not converged
bounded_poolsa pool diverging monotonically: a missing sink, or an intake scaled wrong
ledger_wiredvalue realizing at intake instead of completion, or costs identically zero
stochasticitysuccess pinned at 1.0 — the model is not risk-adjusting at all

A red check blocks the headline number rather than footnoting it. One step later, rdx effect refuses to call a difference a finding when it sits inside ±2 standard errors — the check that stops the workflow manufacturing confident nonsense at the last possible moment.

It is allowed to say no

If nothing is contended, nothing takes time, and no decision is taken inside the horizon, then a spreadsheet is the right tool, and the workflow says so and stops before a model exists. A skill that can qualify out earns more trust than one that always produces a model — and it protects the framework from accumulating a corpus of agent-built models that answer nothing.

Why ReactiveDynamics specifically, and not a general-purpose simulation library

A model here is data: one JSON document, whose every expression is a node-tagged tree drawn from a closed whitelist, whose every host construct is referenced by name through a per-network registry, and which is never parsed-and-evaluated on load. ReactiveDynamics.validate(dict) is a pure static pass returning diagnostics — severity, JSON path, message — and construction is gated on it.

Compare the alternative. A SimPy or AnyLogic model is code; an agent authoring one is doing code generation, with an arbitrary-execution surface and no critic short of running it and eyeballing the output. Here the agent emits structured data, receives machine-readable diagnostics carrying the path to repair, and quotes numbers that replay exactly because determinism is contractual rather than incidental. Closed IR, plus a pure validator, plus (model, seed) reproducibility, is what makes agentic authoring defensible — and all three are properties of the engine's own design, not of a wrapper around it.

2 · How it is built

The division of labour follows the frontier pattern, and is worth stating because the pieces are routinely conflated: skills carry knowledge and procedure; MCP carries capability the model does not otherwise have; a plugin is a distribution unit; subagents buy context isolation; hooks buy deterministic enforcement. Applied here, most of the value lands in the most portable layer — deliberately.

Skills — five, with progressive disclosure · shipped

Five, not ten. The split is by mode, because the modes need disjoint knowledge and disjoint registers, and you do not want the authoring schema loaded into context during a Socratic interview.

SkillRoleWhat it loads
rd-studyorchestrator — owns the study directory, the phase sequence, the qualifying testthe phase map; one phase skill at a time
rd-framethe interview: decision, lever, scarce resource, contention rule, horizon, metrica question bank and the pre-registration discipline — no schema at all

Subagents — three, each for a reason · specified, W9

  • rd-modeler — runs the validate/repair loop in its own context. A repair cycle can burn twenty tool calls on diagnostics that are worthless once fixed; the orchestrator wants the clean document, not the debris.
  • rd-critic — adversarial review of a finished study in fresh context: the code-reviewer analogue, and the one whose absence the demo below actually demonstrates.
  • rd-calibrator — parallel parameter sweeps, where the point of isolation is the volume of numeric output rather than the length of the loop.

The demo is the argument for rd-critic. The one number that study withdrew was invisible to every validator and every plausibility check, because it was a value typed by hand into a summary table with a standard error copied from the line above it. Both rules that would have caught it are now written down as checks for the critic to run.

The MCP server — and why it is not about capability · specified, W8

In Claude Code, running Julia needs no MCP at all: Bash plus a checked-in script is the idiomatic default, and the layer ships those scripts regardless, because they are also what makes it portable to harnesses that have no MCP. MCP earns its place for two specific reasons, neither of which is capability.

  1. A persistent Julia session. Loading the engine plus a plotting stack costs tens of seconds of package load and JIT per cold process. An interactive loop that pays that on every validate, run and redraw is unusable. A long-lived worker turns a ~45-second round trip into a sub-second one, and it can retain the constructed problem between calls — so redrawing an exec map under a different highlight becomes a styling pass over a finished run rather than a fresh simulation.
  2. Cross-client reach. Claude Desktop and other MCP hosts have no shell. The same six-tool surface reaches them unchanged.

What it connects to: nothing external. Worth saying plainly, because MCP usually connotes a third-party service. This is a local stdio server acting as thin transport over the local Julia runtime, calling the engine's own functions. No network egress, no credentials, no remote dependency, nothing leaving the machine.

Two architectural rules keep it honest. rd_validate must call ReactiveDynamics.validate and never reimplement it — a second implementation would fork the trust boundary, and the fork would be the one the agent trusts. And rd_draw must degrade rather than fail when Graphviz is missing, because Graphviz is a system binary rather than a Julia package: an absent diagram must never cost you the study.

One hook · specified, W10

A PostToolUse hook on writes to *.rdj.json, running validate and surfacing the diagnostics inline. Hooks are for deterministic enforcement rather than persuasion: no amount of skill prose reliably prevents an invalid model being left on disk, and a hook makes leaving one silently impossible.

Why the skills cannot drift out of date

A skill that copies the contract becomes a fourth divergent copy of the semantics. So the knowledge is tiered, and only the last tier is hand-written prose.

  1. Pointers, never copies. The skills cite normative sections by number — the contract §1.1 for the modality truth table, §4 for determinism, ADR 0002 for the allocator, ADR 0005/0006 for the IR and the registry boundary — and read the real document at the moment of need.
  2. Generated extracts. agent/reference/model_schema.md is regenerated from the loaded module: the export surface, the document key set, the modality truth table, the operator/distribution/reference whitelists, the attribute defaults. gen_reference.jl --check fails CI on drift, so the skills' API reference is validated by the same suite that validates the engine.
  3. Genuinely new procedural prose — the interview and its question bank, the qualifying test, the check list, the calibration discipline, the briefing template. All procedure, no semantics; it cannot contradict the contract because it does not restate it.

One honest limitation surfaced while building this: the JSON-key ⇒ store-column mapping is function-local inside the serializer rather than an exported table, so that one table is hand-maintained. It is guarded rather than trusted — the generator asserts that every column it names exists in the schema and every key it documents is really read by the engine or the CLI, and refuses to emit if not. That assertion paid for itself immediately by proving two document keys are read by nothing upstream.

3 · The integration surface

Everything mechanical goes through one CLI. Not a library binding, not a REPL protocol — one script, JSON on stdout, exit codes that carry meaning.

julia --project=. agent/scripts/rdx.jl <command> [args] [--flag=value ...]
CommandDoes
validate MODELstatic, eval-free schema check → diagnostics with JSON paths
run MODEL --seed=None seeded run → per-place troughs, per-transition spawns and completions, ledger totals; --trace=P[,P...] adds the full per-tick series, --out=DIR writes an export bundle
diagnose MODEL --seed=Nthe plausibility gate — the nine checks, against the brief's declared intent (--expect-binds=, --expect-reusable=, --tally=)
ensemble MODEL --seeds=N --metric=Mseeded ensemble → mean ± sem and quartiles; --per-seed adds raw member values
effect BASE VARIANT --metric=M --seeds=Ntwo-arm treatment effect Δ ± se, with a significance verdict
draw MODEL --out=PATHthe net; --exec-map --seed=N decorates it with run statistics

Exit codes, and metrics that are names rather than code

0 ok · 1 findings · 2 error. An agent branches on the code and repairs against findings[]; it never has to parse prose, and a wrapper never has to guess whether a non-empty stderr meant failure. That is the whole repair loop's contract.

Metrics are requested by name: final:<place>, min:<place>, max:<place>, sum:<place>, spawns[:<transition>], completions[:<transition>], successes[:<transition>], reward, cost, net, enpv. Deliberately not a callback — letting the caller pass a Julia reduction would reopen the exact code path the JSON document exists to close.

The one place authored Julia executes

--host=FILE. A structured token's Julia type is the only thing a model document cannot carry, so a study that needs real token fields ships a small host.jl defining the type plus a registry mapping kind names to constructors — and rdx prints a notice to stderr every time it includes one, because a code seam that opens quietly is not a seam. Models without structured tokens need no host file at all: the engagement-scale study below has none, which is what makes that entire study pure data.

What a study looks like on disk

<slug>/
  BRIEF.md              phase 1 — decision, lever, scarce thing, failure modes
  host.jl               only if the study uses structured tokens
  model.rdj.json        phase 2 — the baseline arm
  arm_<lever>.rdj.json  phase 2 — one per counterfactual, minimal diff
  DOCTOR.md             phase 3 — the nine checks and their verdict
  FINDINGS.md           phase 4 — the briefing
  figures/              exec map, result plots
  results/              the JSON envelopes every number was read out of

One arm per file, differing in as few lines as possible, is what makes a treatment effect legible: the diff between two documents is the intervention. The engagement-scale study puts three more files beside these — a README.md recording the exact command behind every number, a figures.jl that redraws every chart from results/, and a numbers.jl that re-derives every published table from the same envelopes. If numbers.jl and the prose disagree, the prose is wrong.

Two CI gates, both cheap

.github/workflows/AgentLayer.yml, on any change under agent/ or src/:

# the known-answer study, driven end to end through the JSON document path
julia --project=. agent/scripts/acceptance.jl

# the generated schema reference is not stale
julia --project=. agent/scripts/gen_reference.jl --check

The first drives a published case study's marginal-scientist shadow price through the JSON document path and asserts it still prints delta 18.991 se 2.528. If it prints anything else, the workflow has regressed against the engine — which is what makes it a test rather than a demo. The second is the anti-drift gate above.

Portability — three layers, ordered so the valuable part travels

  1. skills/ + scripts/ — Markdown and Julia scripts over a shell. Any harness that can read a skill and run a command, the Agent SDK included; usable by hand with no agent at all. Shipped.
  2. .mcp.json + the rd server — any MCP host, including clients with no shell. W8.
  3. plugin.json, slash commands, the validate hook — Claude Code specific. W10, W12.

The knowledge and the procedure live in layer 1. A non-Claude harness loses the slash commands and the write-time validate hook; it does not lose the workflow.

4 · How you drive it today

The plugin is not packaged yet, so today's entry point is the orchestrator skill and a repository checkout. That is also the honest portable path: there is nothing in the loop a shell cannot do.

From Claude Code

Point a session at the orchestrator and describe the decision rather than the model:

Read agent/skills/rd-study/SKILL.md and run a study with me. We are looking at in-licensing three clinical assets, and I need to know what they are worth against our own development group — which is already full.

The skill creates the study directory, infers the phase from which files already exist, and reads exactly one phase skill at a time. It will interview before it authors. That is the part users try to skip and the part that determines whether the resulting number is about their system.

What actually runs

The commands are not hidden — they are the artifact. A study the size of the one below is three sequential batteries plus the audit:

S=agent/studies/portfolio_bid; R=$S/results
M='enpv,net,reward,cost,final:own_market,final:acq_market,max:own_p1'
M="$M,successes:adv_own_p2,min:fte"

# 1. the paired comparisons — 120 members per arm, same seed stream both sides
julia --project=. agent/scripts/rdx.jl \
    effect $S/model.rdj.json $S/arm_acquire.rdj.json \
    --seeds=120 --root-seed=2026 --metric=$M > $R/effect_acquire.json

# 2. arm levels — a derived contrast's se is built from arm sems, not effect ses
julia --project=. agent/scripts/rdx.jl \
    ensemble $S/arm_both.rdj.json --seeds=120 --root-seed=2026 --per-seed \
    --metric='enpv,net,final:acq_market,max:own_p1,min:fte' > $R/ens_arm_both.json

# 3. the health report, a single-seed trace, and the diagrams
julia --project=. agent/scripts/rdx.jl \
    diagnose $S/model.rdj.json --seed=1 --expect-binds=fte \
    --expect-reusable=fte --tally=own_market > $R/diagnose_model.json
julia --project=. agent/scripts/rdx.jl \
    run $S/arm_acquire.rdj.json --seed=1 \
    --trace=fte,own_p1,own_p2,acq_p2,own_market,cash > $R/trace_arm_acquire.json
julia --project=. agent/scripts/rdx.jl \
    draw $S/arm_acquire.rdj.json --exec-map --seed=1 --out=$S/figures/exec_map.svg

Run them strictly sequentially. Concurrent Julia processes contend on one package depot and block rather than compute — a practical trap worth naming, because the instinct with nine arms is to fan out.

Resuming, and auditing later

Phase is inferred from which artifacts exist, so a study resumes across sessions with no chat state carried over: the directory is the state. The same property is what makes a number auditable after the fact — the results/ envelopes and the recorded command are enough to re-derive every published figure without rerunning anything, which is exactly what the audit script in the demo does.

Without Claude Code

The skills are Markdown and the CLI is plain Julia over a shell, so any agent that can run a command and read a file can drive this — and a human can drive it with no agent at all. Claude Code's skill and plugin packaging is the distribution mechanism, not the substrate.

Everything above is the capability. What follows is one run of it, on a decision the size of real work.

A VP of corporate development arrives with a term sheet for three clinical-stage assets, a banker's risk-adjusted NPV of about $740M, and a 40-FTE development group that the company's own pipeline already fills. The question is not what the assets are worth. It is what they are worth to us — and the answer turns on a queue.

The dialogue is composed around a finished study: every command shown was really run, and every number is a real 120-seed measurement traceable to the study's provenance file. It is labelled that way deliberately, because the other captured session in this repository is a blind two-agent capture, and the two artifacts are evidence of different things — that one shows what an unrehearsed session looks like, this one shows what the workflow produces when it is driven to completion.

What to watch for, apart from the answer. The session stops one step short of the briefing to audit its own summary table, and withdraws a number. That row was not a modeling error: no validator and no plausibility check could see it, because it was a value typed by hand into a table with a standard error copied from the line above. Re-deriving every published row from the result envelopes is what caught it. Phase 1 — FRAME
Operator

I've got a term sheet in front of me for three clinical-stage assets out of a private biotech — one about to enter Phase II, two behind it. Their banker has a risk-adjusted NPV of about $740 million on the package and they are anchoring hard on it. My board meets in three weeks and I have to walk in with a recommendation and a number.

Here is my problem. Our development group is 40 FTE and it is already full. Every one of them is on our own pipeline — four preclinical programmes, four in Phase II, three in Phase III — and nobody in the building has been able to tell me what happens to those if we drop three more assets on the same people. Claude

Phase 1 of 4 — framing. I want to change your question before I answer it, because the one you asked has an answer you cannot use.

$740M is probably a fair standalone valuation. Standalone means these three assets developed by an organisation that has enough people to develop them. That is the number the seller is entitled to quote, and it is the wrong number for you, because what you are buying is not three assets — it is three assets plus a claim on 40 people who are already busy. One of your Phase III starts holds 10 of those 40 for thirty months. A Phase II start holds 6 for twenty-four. The acquired Phase II asset wants 6 of the same people for fourteen. Nowhere in a discounted cash flow is there a line that says and then it waits.

So the two questions I intend to answer are:

  • **What is this package worth to us, at 40 FTE?** Not to a generic developer — to the group that would actually have to do the work.
  • If we bid, must we also fund the integration capacity, and what is that second cheque worth?

Two decisions, two prices. I will price them separately, because the second one is the only part of this you can still change after the term sheet is signed.

Here is how I get the seller's number and yours out of the same model, which matters for the conversation you are going to have in three weeks. I build one baseline — our pipeline, our 40 FTE, no deal — and every scenario is that baseline plus one change.

Two things I need from you, then I build.

1. The integration cheque. If you did fund capacity alongside the deal, what is the plausible ask — 12 FTE? I will run 4 and 24 as well, so the answer arrives with a dose response instead of a single point.

2. Who goes first. Under contention today, does late-stage work beat early-stage work? My default: our Phase III outranks the acquired Phase II, which outranks our own Phase II, and preclinical goes last. Editorial note. The study this page walks through is finished, and its provenance is a file rather than a claim: agent/studies/portfolio_bid/README.md records the question, the nine documents, every command in the three batteries, and every number those commands produced. Nothing quoted in the conversation above is absent from it. What is composed is the dialogue — there was no VP of corporate development, and the exchange is written around the artifacts rather than transcribed from a live interview. The commands are the ones that ran. The numbers are 120-member measurements off root seed 2026, and they do not move when you re-run them.

Three things are on the page because they are the parts a polished demo cuts.

The failing health check. rdx diagnose returns 7 pass / 1 warn / 1 fail on the baseline, and the failure is right: three transitions never spawn in an arm that never acquires anything. The check cannot know that, and the correct response is to explain it, not to suppress it — the same check comes back 8 / 1 / 0 on the arm that does acquire. The reason to leave it visible is that the alternative sentence, diagnose is green, is what a study says when it has run the gate on whichever arm happened to pass.

The horizon warning, which makes every figure a floor. Both arms warn that work is still in flight at month 120 — 7 firings in the baseline, 9 in the programme arm. That is not a footnote. It is visible in the results as +24 FTE measuring less than +12, and it is why the report hands over floors (Δ less twice its margin) instead of central estimates.

The withdrawn row. The only wrong number the session produced was in a summary table the analyst typed by hand: the interaction between the two cheques, entered as a null, with a value carried over from a different contrast and a standard error copied from the line above it. Every envelope behind it was correct. Re-derived from the arm means and their standard errors the contrast clears — +378 ± 140, 2.71 se — and the audit it triggered also corrected the dose-response test in the other direction, from a margin of 157 to one of 125, because the two dose comparisons share an arm whose variance was being counted twice. Both corrections came from the same rule, which is the transferable part: two effects' margins may be combined only when the two effects share no arm. Nothing in validate or diagnose could have caught a transcription error — those check documents and runs, and this was neither. What caught it was that every number in the study has a command behind it, so it could be re-derived rather than believed. That locates where this workflow is fragile: not in the simulation, and not in the ±2 se rule the CLI enforces on every metric, but in the tables and sentences assembled around the numbers afterwards. A model document can be validated. A hand-copied row cannot.

A quieter piece of the same discipline sits in the DIAGNOSE turn. The obvious way to display a capacity constraint is a saturation percentage — and on that metric this study reads backwards, because the baseline is its most saturated arm: a group with no acquired work is packed tightly into its own pipeline, and a 6-FTE Phase II start cannot fit into the gaps a 40-FTE ceiling leaves. The percentage moves the wrong way for a fragmentation reason that has nothing to do with the decision, so the argument is made from queue-wait and launch counts instead. The most quotable measurement in the study is the one that had to be dropped.

And the boundary, stated once. This is a study of a constraint, not of a price. Per-launch value and the stage probabilities of success are illustrative inputs, not diligence. What is measured is the gap between a valuation that ignores capacity and one that does not — and that gap belongs to the 40-FTE ceiling, the stage FTE loads and the priority order. Change those three and every number on this page moves.

The second cheque is the finding

Twelve FTE are worth −$8M ± $91M on their own — 0.09 standard errors from zero, as clean a null as this study produced — and +$370M ± $106M once you own the assets. Same twelve people, same cost, same document but for one line. Capacity is worthless standing alone in this pipeline and becomes the highest-return line item in the transaction the moment there is acquired work waiting for it. That asymmetry is structurally invisible to an NPV model, which prices the assets and the headcount as separate rows and then adds them: the additive answer would have been −$8M for the people and +$744M for the assets, and it would have been wrong about both. The practical consequence: the integration budget is not overhead attached to the deal, it is the part of the deal that recovers the seller's valuation, and at a floor of $158M it is cheap against any twelve-FTE loaded cost.

The asymmetry can be put as a single question with a single error bar — is the same twelve FTE worth more with the deal than without it? — and it survives being asked that way. The contrast (arm_both − arm_acquire) − (arm_capacity − model) is +$378M ± $140M, 2.71 se from zero: the two levers are complements, and the combination beats the sum of its parts by a floor of roughly $99M. Quote that floor rather than the point estimate — 2.71 se clears this study's bar without much room to spare.

What this study does not support

Reported with the same prominence as the wins, because the nulls are where a briefing like this usually oversells.

  • That the complementarity is worth precisely $378M. The interaction clears at 2.71 se — above this study's ±2·se bar, and not far above it. Its floor is about +$99M, an interaction half this size would not have separated from zero at 120 members at all, and the defensible sentence is "the combination beats the sum of its parts", not the point estimate.
  • That 24 FTE beats 12. +$306M against +$370M, a difference of 64 against a se of 125 (0.51 se). Indistinguishable; fund the cheaper dose. Note the estimator trap underneath that number: those two effects share arm_acquire, so the se has to be rebuilt from the arm sems — differencing the two effect standard errors counts the shared arm's variance twice and inflates it to ~157. A contrast of contrasts is always built from arm sems; differencing effect ses is valid only when the two effects share no arm.
  • A dose-response curve. Three doses are measured — +4 and +12 without the deal, +12 and +24 with it — with sems near 90. Three points do not determine a shape. This supports fund twelve alongside the deal, not twelve is optimal.
  • Anything beyond month 120. Both arms warn horizon_sufficient; every number above is a lower bound.
  • A valuation of the assets themselves. The per-launch rewards and stage success rates are illustrative. The measured quantity is the gap between a valuation that ignores capacity and one that does not, and that gap is a property of the constraint, not of the price.
  • A number for a different organisation. The 40-FTE ceiling, the per-stage FTE loads and the priority order produce the entire result. Change them and every figure moves.

One diagnostic honestly moves the wrong way, and it is worth knowing before someone else finds it. The baseline is the most saturated arm: it sits within one FTE of the ceiling on 96 of 122 ticks (79%), against 81 (66%) with the deal and 52 (43%) with the deal plus twelve people. Utilization falls as the system gets less constrained, for a fragmentation reason — with no acquired work competing, the group packs tightly into its own pipeline, and a 6-FTE Phase II start does not fit the gaps a 40-FTE ceiling leaves once larger programmes are resident. So the argument above is made from queue-wait and launch counts and never from a saturation percentage. A diagnostic that moves the wrong way for a mechanical reason should be dropped, not explained.

Why a spreadsheet cannot produce this

Three assets and unlimited people is arithmetic: value each asset, discount, add. Three assets and 40 shared people is a queue, and a queue's output is not a function of its inputs' averages — it depends on which programme is holding ten people this month, for how long it holds them, and who the allocator admits when both want the same ten. That is why the same three assets are worth +$744M in one arm and +$241M in another with every asset-level input identical, why twelve people are worth −$8M alone and +$370M in combination, and why the third acquired asset waits 31 months in a model where nothing about it changed. No closed form gets to a 31-month wait.
