# ADR 0014 — Visualization: result-plot recipes and the network "exec map"

- Status: Proposed 2026-06-29. The engine's visualization surface is one live function plus dead code. `AlgebraicAgents._draw(prob, vars)` plots species columns from `prob.sol` via Plots.jl (`src/interface/plots.jl:13-31`) — the only working, generic result plot. Everything else is either dead (`src/interface/solve.jl`'s `@plot` macro + `plot_summary`/`plot_ensemble_sol` reference removed SciML `EnsembleSummary`/`EnsembleSolution`, `solve.jl:9,38,45` — orphaned from the pre-ADR-0001 `DiscreteProblem` era) or ad-hoc (the four BD figures are hand-written in `demo/bd_acquisition/figures.jl` against `Plots`/`gr()`, reusable by no other model). And there is NO way to draw the reactive NETWORK itself — no node/arc rendering of the species↔transition structure, no agent-hierarchy/wire diagram. This ADR pins two additive capabilities: (1) a small set of result-plot RECIPES behind a Plots.jl package extension (with the dead code removed), and (2) a three-layer network "exec map" — structure extraction → Graphviz rendering (reusing AA's `run_graphviz`) → a run/ensemble result OVERLAY that colors bottlenecks and highlights token paths, composed with AA's existing `wiring_diagram`. Answers the maintainer's Workstream question: "visualization methods for graphical presentation of the reactive networks … hierarchies, connections, wires … highlight some tokens … an exec map we can analyze for (in)efficiencies … integrate with simulation results to show bottlenecks."

## Context

Two distinct asks, currently both under-served.

**Plotting RESULTS.** The only generic, working plot is `_draw` (species trajectories from `prob.sol`, `plots.jl:13`). Real analysis lives in `demo/bd_acquisition/figures.jl`: a Δ-rNPV waterfall, a synergy decomposition with ±1 SE bars, an rNPV histogram, and a capital-tradeoff line plot — all hand-written `Plots` calls bound to that one demo's data shapes, reusable by nothing else. Meanwhile `src/interface/solve.jl` carries 201 lines of DEAD plotting: `plot_summary`/`plot_ensemble_sol`/`@plot` were written for SciML `EnsembleSolution`/`EnsembleSummary` objects that ADR 0001 removed when it demoted SciML; the types aren't even imported, so the macro is dead-on-arrival. So the result-plotting story is: one trivial recipe alive, the useful plots trapped in a demo, and a pile of orphaned SciML code to delete.

**Graphical presentation of the NETWORK.** There is none. RD is a Petri net but cannot draw itself — no rendering of species (places) and transitions and the arcs between them, no view of the agent hierarchy (the `prob` → `"structured"` container → token tree), no view of the ADR 0012 wires. This is the bigger gap and the one with the most leverage, because the maintainer's framing is not "draw a static schematic" but "an EXEC MAP we can analyze for (in)efficiencies … highlight tokens … show bottlenecks" — i.e. a structure diagram DECORATED with run results.

Crucially, two things make the network view cheap. First, AA ALREADY draws hierarchies and wires: `wiring_diagram(agent)` builds a Graphviz DOT string (nodes = agents, dashed edges = parentship, annotated edges = wires) and `run_graphviz` renders it to SVG/PNG via `Graphviz_jll` (`wires.jl:144`, `graphviz.jl:18`). Emitting DOT is just string-building and rendering reuses AA's machinery — so a Petri-net view adds NO new graph dependency (it fits the ADR 0005 minimalism). Second, the species↔transition incidence is already inspectable data — today as `transLHS` (parsed reactant structs) + `transRHS` (`state.jl:306`, `solvers.jl:662`), and more cleanly once the ADR 0003 `ReactantSpec` table lands — so structure extraction is a walk over existing fields, no re-parsing of `Expr`s.

So the work is two additive pieces that share Plots/Graphviz infrastructure RD or AA already has.

## Decision

### (A) Result-plot recipes behind a Plots.jl extension — and delete the dead code

**1. Delete the SciML orphans.** Remove `plot_summary`, `plot_ensemble_sol`, `first_sol`, and the `@plot` macro from `src/interface/solve.jl` (the `EnsembleSummary`/`EnsembleSolution` paths, `:7-201`), and the never-called `plot_df` from `src/interface/plots.jl:3-10`. Keep `@agentize` (the live export at `solve.jl:1`) and the `_draw` reduction (generalized in A3). This is pure removal of code that cannot run on `ref-agents`.

**2. Recipes, not bespoke functions, behind an extension.** Implement the plot set as Plots.jl `@recipe`s in a package extension `RDPlotsExt` (loaded only when `Plots` is present), keyed off the RAW result artifacts (`prob.sol`, `prob.log`, `program_ledger(prob)`, ADR 0013's `token_trajectory`/`ensemble`) so they work on ANY model, not just BD. Recipes are declarative and user-composable (a caller can restyle/overlay), which is why they beat the demo's imperative `Plots.plot!` chains.

**3. The recipe set** (each consumes documented artifacts, so each is model-agnostic):

| # | Recipe | Reads | Answers |
|---|---|---|---|
| 1 | Marking trajectory | `prob.sol` | species/token counts over time (generalizes `_draw`) |
| 2 | Resource utilization / saturation | `:saturation` + `:allocation` log rows (`solvers.jl:444,521`) | where pools bind — the demo's cash/scientist troughs, made reusable |
| 3 | Valuation / rNPV curve | `:valuation` rows (`solvers.jl:1024`) + `program_ledger` | portfolio + per-program value over time |
| 4 | Per-program ledger | `program_ledger(prob)` DataFrame (`ledger.jl:201`) | stacked cost/reward or waterfall per token |
| 5 | Token trajectory + envelope | ADR 0013 `token_trajectory`/`trajectory_envelope` | a token's attribute path; the "typical" median+IQR band |
| 6 | Ensemble distribution / treatment effect | ADR 0013 `ensemble`/`summarize`/`treatment_effect` | per-run metric histogram/box; the Δ-rNPV waterfall + synergy decomposition |
| 7 | Throughput | `:new_transitions`/`:terminated_*` rows (`solvers.jl:340,768`) | firings/terminations per tick |

The four bespoke BD figures become instances of recipes 6 (waterfall + synergy decomp + rNPV distribution) and 2 (capital tradeoff), so `demo/bd_acquisition/figures.jl` shrinks to a styling layer over the engine recipes.

### (B) The network "exec map" — three separable layers

The design principle: keep STRUCTURE dependency-free and pure data; make RENDERING and the RESULT OVERLAY additive layers on top. So a user can extract/inspect the graph with no plotting deps, render it with Graphviz, and decorate it with run results — each step optional.

**Layer A — structure extraction (dep-free, pure data, no run needed).** `network_graph(prob_or_spec) -> NetworkGraph`: a plain inspectable value (species nodes, transition nodes, arcs LHS→T and T→RHS with stoichiometry + modality labels) built by walking the incidence — today `transLHS`/`transRHS` (`state.jl:306-307`), cleaner over `ReactantSpec` when ADR 0003 lands. Round-trippable from the JSON model alone (no simulation), so the diagram is authorable-time documentation as well as a run artifact.

**Layer B — static rendering (reuse AA's Graphviz, compose with the hierarchy).** `to_graphviz(NetworkGraph) -> String` emits Petri-net DOT (species = circles, transitions = boxes, arcs with stoichiometry labels, arc COLOR by modality from the §1 truth table — consumed/conserved/block/nonblock — and transition nodes annotated with rate/priority/cycletime). `draw_network(prob; format)` renders it via AA's `run_graphviz` (`graphviz.jl:18`). The composition move: render the RD net as a Graphviz CLUSTER and embed it INSIDE AA's `wiring_diagram` (`wires.jl:144`), so the ADR 0012 `inputs[]`/`observables` ports show as cross-cluster wire edges to sibling agents. That makes ONE map of the whole system — the AA hierarchy with each RD net expanded inside it — instead of two disconnected pictures. (Mermaid via `agent_hierarchy_mmd`, `utils.jl:191`, is the lightweight alternative for the hierarchy-only view.)

**Layer C — the result overlay (the "exec map" / inefficiency view).** `exec_map(prob_or_ensemble; highlight)` decorates Layer A's nodes/arcs with statistics from a finished run or ensemble (ADR 0013 data):
- species node FILL = pool level / trough depth (from `prob.sol`) → starved resources glow;
- transition node = throughput (firings) or SATURATION (the `:saturation` log row, `solvers.jl:444`) → **bottlenecks colored hot** (this is the maintainer's "(in)efficiency" read);
- arc THICKNESS = flow volume (allocation/terminations);
- **token highlighting**: a selected token's `past_bonds` trail (`(species, t, transition)` triples, `agents.jl:141-143`) drawn as a colored path THROUGH the net — "where did this program go"; or all tokens snapshotted at their current `bound_transition` — "where do programs pile up." The selection is a `TokenPredicate` (ADR 0008), so `exec_map(prob; highlight=@select(Project, phase==:Phase3))` lights the Phase-3 cohort.

Because Layer C only CONSUMES the ADR 0013 statistics, the result→map integration is free: the same `:saturation`/`token_trajectory`/`ensemble` data that feeds the recipes (A) feeds the overlay, so "show the bottlenecks on the map" is a styling pass, not a new computation.

### (C) The primary view is the Petri net; the AA tree is the composed frame

Two diagrams could be "the" diagram: the Petri net (species/transitions — the modeler's mental model) or the AA agent tree (`prob` → `"structured"` → tokens + wires — what AA draws natively). They answer different questions. Decision: the Petri net is the PRIMARY view (Layers A/B), and the AA tree is offered as the OUTER FRAME via Layer B's cluster embedding — so the two reconcile into one image (the hierarchy with nets expanded inside) rather than competing as separate features. A token is NOT drawn as its own AA node in the primary view (there can be thousands); tokens appear only as overlay decoration (Layer C) on the species/transition they occupy.

## Consequences

- Result plotting becomes a model-agnostic recipe set (A) instead of one trivial reduction + a demo's bespoke figures + dead SciML code; the BD figures collapse onto recipes 2/6.
- The network gains a graphical representation at THREE depths — inspectable data (A), a rendered diagram composable with the AA hierarchy/wires (B), and a result-decorated exec map (C) — with NO new graph dependency (Layer B reuses AA's `wiring_diagram`/`run_graphviz`; Plots is already a dep, Graphviz arrives via AA's `Graphviz_jll`).
- The exec map directly serves the maintainer's diagnostic intent: bottleneck coloring from `:saturation`, starvation from pool troughs, token-flow highlighting from `past_bonds`/`@select` — read off one picture.
- Dead-code removal (A1) shrinks `solve.jl` by ~190 lines and removes the misleading "we have ensemble plotting" surface (it never worked on `ref-agents`).
- Costs: the `RDPlotsExt` extension with seven recipes + the deletions (A); `network_graph`/`NetworkGraph` structure extraction (B-A, dep-free), `to_graphviz`/`draw_network` DOT emission + AA-cluster composition (B-B), `exec_map` overlay reading ADR 0013 stats (B-C). Layer A is buildable on the CURRENT `transLHS`/`transRHS` incidence; it simplifies (typed FKs, no reactant re-parse) when ADR 0003's `ReactantSpec` lands — a clean-up dependency, not a blocker.
- One soft dependency: the most useful overlays (recipe 5, token-path highlighting, ensemble band) need ADR 0013's `token_trajectory`/`ensemble`. Layers A/B and recipes 1–4/7 stand alone without 0013.

## North-star tie-in (BD)

The pharma pipeline draws as a Petri net: `Project`-in-phase places, the five `@advance` transitions, the `scientist` (conserved) and `budget` (rate) resource arcs, the `financing` source. `draw_network(prob)` colors the conserved scientist arcs distinctly from the consumed budget arcs (§1 modality). Embedded as a cluster inside the ADR 0012 hierarchy diagram, the macro/market sibling agents and their `ExternalRef` wires (`ext_rate`, `market_sentiment`) appear as edges INTO the net — the whole coupled BD model on one map. Then `exec_map(ensemble(deal); highlight=@select(Project, acquired==true))` paints the binding budget pool hot, thickens the high-throughput Phase-2→Phase-3 arc, and traces the acquired programs' paths through the ladder — making the acquisition's bottleneck-relief story (the BRIEF's whole point) a single annotated diagram rather than four separate figures.

## Invariants

1. **Structure is pure data.** `network_graph` builds with no Plots/Graphviz dependency and no simulation; it is a function of the model spec alone (round-trippable from JSON, §6).
2. **Rendering is reuse, not reinvention.** `draw_network` emits DOT consumed by AA's `run_graphviz` (`graphviz.jl:18`); the hierarchy/wire composition reuses AA's `wiring_diagram` (`wires.jl:144`). No new graph library is added.
3. **The overlay only reads.** `exec_map` decorates Layer A with finished-run/ensemble statistics (ADR 0013); it never mutates state or re-runs dynamics.
4. **Highlighting is a predicate.** Token highlighting is scoped by a `TokenPredicate` (ADR 0008), so a highlighted cohort is exactly a `@select` set — the same selection semantics as the model dynamics.
5. **Recipes are model-agnostic.** Every recipe consumes a documented raw artifact (`prob.sol`/`prob.log`/`program_ledger`/`token_trajectory`/`ensemble`), so it works on any model; none hard-codes BD fields.
6. **No dead viz code.** The SciML `EnsembleSummary`/`EnsembleSolution` plot paths (`solve.jl`) and the unused `plot_df` are removed; every shipped viz entry point runs on `ref-agents`.

## Open questions

- **Extension vs core for the recipes.** Plots is currently a hard dep (`Project.toml`), but the ADR 0005 minimalism push may demote it to a weakdep. Lean: author recipes in `RDPlotsExt` from the start so the choice is just whether `Plots` is in `[deps]` or `[weakdeps]` — the recipe code is identical either way.
- **Graphviz availability.** `run_graphviz` uses `Graphviz_jll` if present else a system `dot` (`graphviz.jl`, `requires.jl:31`). Decide whether RD declares `Graphviz_jll` (via AA) as a guaranteed renderer or documents `draw_network` as returning a DOT STRING the user renders, with rendering best-effort. Lean: return DOT always, render when a backend is available.
- **Exec-map layout at scale.** Graphviz `dot` layout of a large refined net (ADR 0009) with hundreds of transitions may be unreadable. Decide whether to expose layout engine choice (`prog=:dot|:neato|:fdp`) and a refinement-collapse option (draw an abstracted process as one node, expand on demand) — ties to the ADR 0009 refine/abstract FK-splice.
- **Overlay color semantics.** Fix the conventions (which colormap = saturation, what "hot" means, log vs linear scaling for flow thickness) so exec maps are comparable across runs/scenarios; document them as the §15 overlay legend rather than leaving them per-call.
- **Animation / time-stepping.** A static exec map shows end-of-run or ensemble-mean state. A time-stepped/animated map (per-tick frames from `token_trajectory` + `prob.sol`) is a natural extension but heavier (a frame sequence + GIF/video dep). Out of scope here; note as future work gated on a real need.
- **Per-recipe ensemble bands.** Recipes 1–3 have natural single-run and ensemble-band forms (median + IQR ribbon). Decide whether each recipe auto-detects `prob` vs `EnsembleProblem` (ADR 0013 B2) and switches form, or whether the band is a separate recipe. Lean: dispatch on the input type so `plot(ens)` bands automatically.
