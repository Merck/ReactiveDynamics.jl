# ADR 0004 — Runtime mutation contract (append-only, mutate-during-simulation)

- Status: Accepted (maintainer-required, 2026-06-18)
- Relates to: ADR 0001 (native engine), ADR 0002 (eval-free hot-loop guardrail), ADR 0003 (typed IR — the append-only invariant carries over to the new store), ADR 0005 (a JSON patch document is the serialized form of a mutation).

### Status note

Accepted — maintainer-required. Mutation during simulation is a hard requirement from the maintainer rulings (add reactions/transitions, and the species/params they reference, mid-run); this ADR pins the contract that makes it sound against the current `ReactionNetworkProblem` runtime (ADR 0001) without violating the eval-free hot loop (ADR 0002).

### Context

The live `ReactionNetworkProblem` must support adding species, params, and transitions while a simulation is in progress — the north-star acquisition lever injects candidate programs and perturbs operational parameters mid-run. The runtime as built makes this possible but only under one structural constraint, because of how attribute expressions are compiled. Every compiled attribute closure hard-codes a species' position as `state.u[i]` using a varmap built ONCE at construction (`compilers.jl:132`, `compilers.jl:149`; substitution at `recursively_substitute_vars!`/`wrap_expr`, `compilers.jl:28-44,110`). The runtime's dimension and name→index oracle is `state.acs`: `nparts`/`parts` delegate to the acs (`state.jl:223-229`), `find_index` reads species names from the acs (`state.jl:170-172`), and `escape_ref(..., state[:,:specName])` resolves names against it (`reaction_parser.jl:36`). The compiled per-tick recipe table is produced by `compile_attrs` (`compilers.jl:145-180`), and the per-tick sampler `sample_transitions!` walks `1:length(state.transition_recipes[:trans])` and indexes EVERY recipe column positionally by that `i` (`state.jl:178-191`). Because of these position-by-index dependencies, the only safe direction of growth is append-only: a new species must take the next index `nparts+1`, `state.u` must grow in lock-step, and the frozen `wrap_fun`/varmap must be re-derived so new expressions can bind the new names. The only mid-run reindexer in the engine — `operators/equalize.jl:52`'s `rem_parts!(acs,:S,...)` — would break every position-indexed closure and must be forbidden while live. Two soft-deactivation mechanisms already exist latently: the `transActivated` flag (set at `compilers.jl:174`, honored as a skip-gate at `state.jl:179`) and the `transToSpawn` deferral column (`compilers.jl:175`).

### Decision

We adopt an APPEND-ONLY runtime-mutation contract: the live model grows monotonically, never reindexes, and removes only logically (soft-deactivate). Mutation occurs strictly at a tick boundary (between `_step!` calls), never mid-tick, so it inherits all of the operational-semantics (CONTRACT §3.3) and determinism (§4) guarantees and consumes no RNG.

**The append-only + soft-deactivate invariant.** New species, params, and transitions receive the next free index; existing indices never move (`index(s) = nparts(acs,:S)+1` at add time, permanent). Deletion and reordering are forbidden mid-run: `rem_part!`/`rem_parts!` on `state.acs` must not run while the model is live (the sole offender is `operators/equalize.jl:52`). Logical removal is `transActivated[i] = false`, which `sample_transitions!` skips (`state.jl:179`) while the row, its index, and all higher indices stay put; in-flight instances of a deactivated transition still run to completion because `finish!` iterates `ongoing_transitions` independently of `transActivated` (`solvers.jl:406`) — the correct business semantics (stop starting new programs, never vaporize running ones).

**The mutation API on the live state.** A small surface operates directly on the live `ReactionNetworkProblem`, each asserting it is at a tick boundary and each returning the new index: `add_species!(state, name; initval=0.0, cost, reward, valuation, modality, structured)`, `add_param!(state, name, val)`, `add_transition!(state, rate, reaction; name, priority, cycletime, prob, capacity, maxlife, multiplier, preAction, postAction, activated=true)`, and `activate!`/`deactivate!(state, sel)`. Each mutator performs a single transactional growth: (1) `add_part!` onto `state.acs` (plus `assign_defaults!`, `ReactiveDynamics.jl:146`) to advance the oracle and assign the next index; (2) grow the live runtime in lock-step — `push!(state.u, initval)` for species, and `push!` the compiled value onto every column of `state.attrs` (species attrs) or `state.transition_recipes` (transition attrs), MIRRORING the `compile_attrs` loop (`compilers.jl:156-172`); (3) for transitions, also push the out-of-band columns that `compile_attrs` adds after the schema columns and that the sampler indexes positionally — `transActivated` (`compilers.jl:174`), `transToSpawn` (`compilers.jl:175`), `transHash` (`compilers.jl:176-177`), and the recipe body `trans` — so every column ends at length `nparts(state,:T)`; (4) widen the `sol` DataFrame by backfilling a column for a new species (`sol` columns are fixed at construction, `solvers.jl:588-591`, and `save!` splats `state.u` into it positionally, `state.jl:92`, so a grown `state.u` without a widened `sol` throws an arity mismatch on the next tick). The `reqs`/`qs` buffers need no manual resize: `evolve!` rebuilds them as `zeros(nparts(state,:S), nparts(state,:T))` and `zeros(nparts(state,:T))` every tick (`solvers.jl:137-138`), and the ongoing buffers size from `length(state.ongoing_transitions)` (`solvers.jl:232`). `add_transition!` must ensure every species referenced by `reaction` exists first, auto-`add_species!`ing any missing ones BEFORE refreshing the varmap (mirroring the `merge_acs!` reactant loop, `ReactiveDynamics.jl:211-214`) — this ordering (add species → refresh → compile transition) is load-bearing.

**The `wrap_fun`/varmap refresh mechanism.** `state.wrap_fun` closes over a varmap built once at construction (`compilers.jl:149-153`) that maps only construction-time names; a new species/param is absent from it, so an expression referencing the new name would compile to a closure that throws on first read. A `refresh_wrap_fun!(state)` re-derives `state.wrap_fun` over the CURRENT acs using the same template as `get_wrap_fun` (`compilers.jl:129-138`): `varmap[name] = :(state.u[$i])` over `enumerate(collect(state.acs[:,:specName]))` and `varmap[name] = :(state.p[$(QuoteNode(name))])` over the param names. Because indices are append-only (the invariant above), the refreshed varmap maps every PRE-EXISTING name to the SAME `state.u[i]` it had before, so already-compiled closures remain valid and are NOT recompiled — only new expressions, compiled at add-time through the new `wrap_fun`, see the extended map. `state.wrap_fun` is a mutable field (`wrap_fun::Any`, `state.jl:61`), so reassignment is safe.

**Compile-on-add, not per-step-eval.** A new transition's sampleable expression attributes (rate, priority, cycletime, prob, capacity, …) are compiled to closures EXACTLY ONCE, at `add_transition!` time, by calling the freshly refreshed `wrap_fun` on each raw attr and pushing the resulting closure into the recipe column (same shape `compile_attrs` produces, `compilers.jl:167-172`). Per tick, `sample_transitions!` only `context_eval`s the already-compiled closure (`state.jl:189`; `context_eval` = `Base.invokelatest(o, state, transition)`, `state.jl:67-71`), identical to existing transitions. `Base.invokelatest` also shields the freshly-`eval`'d closure from world-age errors, so a transition added at t=10 is callable at t=10.

> CAVEAT — the hot loop is NOT fully `wrap_fun`-free TODAY. The current engine still calls `state.wrap_fun(...)` *inside* `evolve!`/`finish!` for three classes of attribute that `compile_attrs` does NOT pre-compile: `transPreAction`/`transPostAction` (read raw from `state.acs` and wrapped on the fly at `solvers.jl:227,485`), per-reactant `stoich` (`solvers.jl:420,430` and `state.jl:201`), and the structured-RHS expressions (`solvers.jl:340,353,369,392`). So the "compile once, never `wrap_fun` in the loop" property is an ASPIRATION the ADR-0002 guardrail sets, not the current reality. For the mutation contract this means: an injected transition whose actions/stoich reference a NEW species depends on the refreshed `wrap_fun` being correct AT hot-loop time (it is, given the append-only varmap refresh), but the broader rework should additionally move these three classes into the compile-on-build recipe so the steady-state loop becomes genuinely eval-free. Until then, `refresh_wrap_fun!` correctness is load-bearing for these in-loop wraps, not merely for `add`-time compilation.

### Consequences

The runtime gains a sound mid-run growth path with a single hard rule (append-only) and an explicit, assertable post-condition set, at the cost of a small live-model API and a `refresh_wrap_fun!` call per add-batch. The acquisition north-star becomes expressible as ordinary tick-boundary operations. The contract introduces a two-source-of-truth window between `state.acs` and the compiled columns: `add_part!` and the column `push!`es must be transactional (or assert equal lengths at the end), because if they desync, the sampler's positional loop (`state.jl:178-191`) silently misaligns columns. `equalize!`/`@join` and any other reindexing macro must consult a runtime `live` guard and refuse on a stepping model — documentation alone is insufficient since these macros operate on the same `ReactionNetworkSchema` type. Observables and structured tokens need their own append-aware handling (below). This contract is written against the current acs-as-oracle runtime; when the ADR-0003 typed-IR store swap lands, `nparts`/`parts`/`find_index` re-point at the new IR's length/name-index, but the append-only invariant and the `wrap_fun`-refresh design carry over unchanged.

### North-star tie-in (acquisition = mid-run add_transition!/perturb)

An acquisition is a mid-simulation lever applied at a tick boundary in one of three shapes. (a) Inject a program: `add_transition!` introduces a candidate program entering at a pipeline phase — e.g. advance to t=10, then `add_species!(sim, :AcqPhase2; initval=3)`, `add_param!(sim, :acq_pos, 0.6)`, `add_transition!(sim, :(0.4), :(AcqPhase2 --> Phase3); name=:acq_p2_to_p3, cycletime=8.0, prob=:(acq_pos), priority=2.0, capacity=5)` — with auto-`add_species!` for any new cohort/param the reaction references. (b) Perturb operational params: capacity/PoS/cycle-time shifts via the existing `set_params` (`state.jl:246-249`) for param-valued attrs, or a direct recipe-column value assignment at a tick boundary, with no index churn. (c) Retire a line: `deactivate!(sim, :legacy_prog)` flips `transActivated` (INV-3); in-flight instances run to completion. rNPV pre/post is the diff of the discounted `:valuation`/`:valuation_reward`/`:valuation_cost` log streams (`solvers.jl:304-312,505`) between two SAME-seeded runs that differ only by the lever; determinism (CONTRACT §4) attributes the entire difference to the lever. For deterministic ensembles, an injected transition SHOULD be given an explicit stable `name` — `name=missing` falls back to `gensym()` (`compilers.jl:177`), which is unique per call but not reproducible across runs.

### Invariants preserved

- **INV-1 Append-only indices.** New species/params/transitions get the next free index; existing indices never move. `length(state.u) == nparts(state,:S)` and `state.u[i] ↔ acs[i,:specName]` hold at every tick boundary (the alignment `find_index`/`state.jl:170` and `escape_ref`/`reaction_parser.jl:36` assume).
- **INV-2 No mid-run reindex.** No `rem_part!`/`rem_parts!` on `state.acs` while live; the sole offender `operators/equalize.jl:52` must refuse under a runtime `live` guard.
- **INV-3 Soft deactivate only.** Logical removal is `transActivated[i]=false` (`compilers.jl:174`, gated `state.jl:179`); rows and higher indices stay put; in-flight instances complete (`solvers.jl:406`).
- **INV-4 Non-negativity & determinism unchanged.** New species enter with `initval ≥ 0`; new transitions use the same ADR-0002 allocator and seeded Poisson/Binomial draws; mutation happens at a tick boundary and consumes no RNG, so `all(state.u .>= 0)` and all §3.3/§4 ordering guarantees hold.
- **Column-length post-condition.** `all(length(col) == nparts(state,:T) for col in values(state.transition_recipes))` and the pre-existing species/transition index map is unchanged (snapshot-compare in tests).

### Open questions

- **Observables refresh.** `state.observables` are compiled once over the construction-time varmap (`state.jl:94-117`); one referencing a newly added species will silently fail to bind. An `add_observable!`/per-observable recompile path is required and is NOT covered by `refresh_wrap_fun!` (observables capture their own varmap at compile time). Should `refresh_wrap_fun!` optionally recompile dependent observables, or stay orthogonal?
- **Structured tokens.** A new species with `structured=true` must `push!(state.structured_token, name)` (`state.jl:50`); `update_u_structured!` (`solvers.jl:630-639`) and genesis binding (`solvers.jl:194`) enumerate `acs[:,:specName]` by position and are append-safe. Is the structured-token vector the right second source of truth, or should `structured` be an acs attribute column to keep one oracle?
- **`add_to_spawn!` defect.** The capacity-overflow deferral `add_to_spawn!` (`state.jl:251-256`) is currently broken — `findfirst` is passed a scalar `length(...)` rather than a range, and on match it increments `transHash` instead of `transToSpawn` (documented in CONTRACT_DRAFT.md Invariant 3). The mutation API maintains the `transToSpawn` column but does not depend on this function; should the fix land in this ADR's scope or separately?
- **`sol` widening policy + mechanism.** When `add_species!` widens `sol`, this is a STRUCTURAL DataFrame operation, not a forward append: `sol` already holds saved rows (`save!` runs at `_step!` start when non-empty and at each tick end, `solvers.jl:644-646,670`; `push!` splats `state.u` at `state.jl:92`), and DataFrames requires all columns to be equal length, so adding a column must supply a value for EVERY existing row at once (`insertcols!(sol, :NewSpec => fill(v, nrow(sol)))`), or the next `save!` throws an arity mismatch. Open: backfill with `0.0` or `missing` — i.e. is "the species did not exist yet" semantically zero or absent, and does downstream rNPV integration need to distinguish them? (A `0.0` backfill is simplest and matches "the pool was empty"; `missing` is more honest but complicates the numeric ledger reductions.)
- **Genesis primitive (carried from maintainer ruling 5).** Whether the Poisson genesis is the right primitive for business processes is out of scope here but interacts with mutation: an injected program's spawn intensity is itself a per-tick draw, so a future genesis-mode change would extend `add_transition!`'s parameterization.
